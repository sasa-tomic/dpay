# dpay codebase analysis

> **Living document.** This is a structural analysis of the dpay codebase — architecture health, where the design earns its keep, and risks to flag before a coding session. It is maintained alongside the code: when a change materially affects anything stated here (a risk resolved, a new surface added, an invariant changed), update this file in the same change.
>
> Last reviewed: see `git log` for this file. Scope: everything under the workspace (`dpay-core`, `dpay-canister`, `dpay-canister-tests`, `dpay-mock-minter` [test-only], `dpay-relay`, `dpay-ffi`, `dpay-sim`, `dpay-fixture`, `e2e/`, `app/`). (The old `ui/` parallel-component harness is deleted — `e2e/` now drives the real app.)

## Architecture health: strong

The single most load-bearing decision — **one Rust core shared by every consumer** — is actually enforced everywhere:

- `dpay-core` (`lib.rs` 454 lines + `nfc.rs` 1663 lines) is the source of truth for signing, validation, codec, and NFC framing. The canister, relay, sim, fixture, and FFI all import it; the app reaches it via UniFFI → `libdpay_ffi.so`. There is no parallel JS/Kotlin reimplementation of money logic.
- Money-critical JS (`app/src/payments.ts`) is intentionally pure + jest-tested and stays on outcome classification (settled/rejected/unknown), never on signature math. Correct separation.

The wire format is frozen and byte-precise (`SIGNING_LEN=100`, `WIRE_LEN=196`, `REQUEST_LEN=68`), and `validate()` is pure/allocation-free — exactly what a canister hot path wants. Field order is documented as FROZEN, which is the right discipline for a protocol surface.

## The canister is a FACADE over external ICRC ledgers (not the ledger)

`dpay-canister` (`ssqti`) holds **no balances**. It is a pure facade with three jobs plus the offline-payer authorization gate:

1. **index** — a registry `currency(u32) -> {ledger principal, mintable}` (`LEDGERS`, stable), populated at init and extendable via `register_ledger`.
2. **routing** — `pay()` resolves the wire's `currency` to its ledger and settles there via the uniform ICRC interface (`icrc1_transfer` / `icrc1_balance_of` / `icrc1_fee`).
3. **cache** — a display-only `BAL_CACHE` backs the fast `balance_of` *query*.

PLUS the **authorization gate** (Ed25519 sig verify + nonce replay protection + expiry/cap), which stays *in the facade* — that is the offline-payer value-add, not ledger logic. Every currency = one real ICRC ledger canister (the DFINITY `ic-icrc1-ledger`); the facade routes every payment through this one interface.

PLUS a **deposit-proxy surface** (ckBTC-style top-up) — four `#[update]` endpoints that proxy an external chain-key minter so the wallet can show a per-account native deposit address, poll for a confirmed mint, and read static deposit instructions: `deposit_address` / `refresh_deposit` / `deposit_info` (no auth — see risk 7) plus `register_minter` (admin-gated by the same `require_admin` controller as `register_ledger`). The minter principal per currency lives in a separate stable map `MINTERS` (`MemoryId 8`; value = `PrincipalStorable`, a principal newtype that serializes the raw ≤29 bytes with no present-flag — absence is expressed by map membership). **KEY INVARIANT:** the minter is always called with `owner = Some(canister_self())`, `subaccount = Some(pubkey)` (`minter_call_btc_address` / `minter_call_update_balance`, lib.rs), so the mint lands on the currency's ICRC ledger at exactly `Account{owner: facade, subaccount: pubkey}` — the *same* account `account_of` (lib.rs:578) hands to `icrc1_balance_of` / `pay` / `transactions_of`. **Subtle encoding requirement (load-bearing):** the REAL ckBTC minter (`mqygn-kiaaa-aaaar-qaadq-cai`, verified via `dfx canister metadata … candid:service --network ic`) takes exactly ONE record argument `(record { owner: opt principal; subaccount: opt blob })` for `get_btc_address` / `update_balance`. The facade encodes this as a candid **1-tuple** `(MinterAccount{ owner, subaccount },)` passed via `Call::with_args(&arg)` — `with_args` on a 1-tuple emits ONE argument (the record). A 2-tuple `(Option<Principal>, Option<Vec<u8>>)` would instead emit TWO positional args and the real minter TRAPS with `IC0503 ... Fail to decode argument 0 ... Subtyping error: Type mismatch` (this exact trap shipped to mainnet once; see below). The single/zero-arg minter proxies and all ledger calls are unaffected. This invariant is pinned by the PocketIC deposit test + a direct mock-contract honesty guard (see "Offline proof status" below). The deposit surface is therefore **purely informational + orchestration**: it changes nothing about settlement, balance, or history — once a mint confirms, the existing balance/history reads reflect it with no code change. dpay never holds the deposited BTC (the minter does the chain-key work and credits the ledger directly), so the non-custodial posture is intact.

**Money-safety rule (load-bearing):** `pay()` ALWAYS reads the AUTHORITATIVE ledger balance (`icrc1_balance_of`) before transferring. The cache is DISPLAY-ONLY — a stale cache (someone transferred directly on the ledger) can only make a shown number wrong, never cause a bad settlement. The cache is refreshed (re-read from the ledger) after every successful `pay` / `mint` / `burn`.

## Withdrawal proxy (ckBTC → native BTC out) — the one-way valve's other direction

`withdraw(WithdrawRequest)` is the mirror of the deposit proxy: where `refresh_deposit` mints ckBTC IN, `withdraw` burns it OUT to a native BTC address on a **verified user Ed25519 signature** (the non-custodial gate — the facade rebuilds the canonical `WithdrawAuth` from the candid fields, recomputes `signing_bytes()` in `dpay-core`, and verifies the sig under `from_pubkey` == the debit subaccount BEFORE moving funds). Flow: `icrc2_approve(minter, amount)` → minter `retrieve_btc_with_approval` (which consumes the allowance via `icrc2_transfer_from` and sends BTC). Idempotency mirrors `pay`: the withdraw nonce is reserved synchronously (no await) in a SEPARATE `WITHDRAW_NONCES` map (MemoryId 12) before any cross-canister call; released on a transient/pre-burn failure (same-auth retryable); settled once the burn commits (the auth can never replay → no double-burn). Min withdrawal = `RETRIEVE_BTC_MIN_AMOUNT = 50_000` sats (mirrors the live minter's `retrieve_btc_min_amount`, verified via `get_minter_info`). Proven offline on PocketIC through the real facade + `dpay-mock-minter` (`crates/dpay-canister-tests/tests/withdraw.rs`: debits+burns-supply, double-withdraw rejected, wrong-sig rejected, below-min rejected, mock-minter honesty guard). The relay surfaces it at `POST /api/v1/withdraw` (`Ledger::withdraw` trait + `FakeLedger`/`AgentLedger` impls) and the app's `WithdrawSheet` signs on-device via the FFI's `sign_withdrawal`.

**Residual front-running risk (documented, inherent to `retrieve_btc_with_approval`):** the approve + retrieve are two cross-canister calls with an `await` between them; in principle a separate caller could invoke the minter's `retrieve_btc_with_approval` with the same subaccount + an attacker address in the gap, consuming the allowance. The blast radius is bounded to the EXACT authorized `amount` (the approval is single-use, for that amount) — never the user's whole balance. This is inherent to the ckBTC withdrawal design (the minter has no signature-binding-the-destination path); the reference NNS minter clients accept the same residual. See risk 8.

## Where the design earns its keep

- **Consent model is sound.** `PaymentRequest` carries no `from`/sig; `to_authorization(from)` copies everything verbatim, so the payer's signature binds exact amount+payee+nonce+currency. The `request_id` doubling as the nonce is elegant — single-scan single-use kills double-charge by construction.
- **Per-currency segregation is across *canisters*, the strongest no-swap guarantee.** A user pubkey maps to ICRC-1 `Account{owner: <facade>, subaccount: <pubkey>}` on each ledger independently. Funds in currency X physically cannot be drawn by a payment naming currency Y — they live on a different ledger canister. This is stronger than a per-currency map key inside one canister. Proven by `currencies_cannot_cross`.
- **Cross-canister atomicity + replay safety is handled honestly.** `pay()` spans `await`s (balance/fee/transfer), and the IC interleaves messages at await points. The nonce is **reserved synchronously before any transfer** (no await in the reserve), so a concurrent `pay` with the same nonce observes it as used and is rejected. Proven by `concurrent_pay_same_nonce_settles_once` (the double-spend regression). On a transient ledger failure the reservation is released (same nonce retriable); on `Ok`/`Duplicate`/permanent-error it stays spent. Defense-in-depth: `created_at_time` is quantized so a sequential retry of the same authorization lands in the ledger's `Duplicate` bucket → no second debit. (The airtight close is an `icrc3_get_blocks` reconcile on restart — a production item, not yet implemented.)
- **NFC transport reuses the exact QR bytes.** Same 196-byte wire, same `verify()`. The HCE/reader state machines are panic-free (`card_never_panics_on_arbitrary_input` proptest) and carry a `SessionPhase` the UI renders directly. AID registered under `category="other"` deliberately to avoid the Google Wallet clash — a subtle real-world trap handled correctly.
- **Relay is honest about failure modes.** `LedgerError::{Rejected(422), Transient(503)}`, retry only on Transient, idempotency keyed by nonce, `committed` guard stops transport errors overwriting a decided ledger outcome, reconcile via `/receipt/:nonce` before reporting failure. This is the "relay must be rock solid" requirement, met. The `Ledger` trait + `AgentLedger` are canister-agnostic (the relay targets the facade `ssqti` by configured id); the only facade-specific detail is that `mint`/`burn` are controller-gated `Result<nat64,text>` updates — `mint` returns the **new balance** (matching the `Ledger::mint` contract that the faucet surfaces directly as `{balance}`), `burn` returns the ledger block index (facade-internal, no relay consumer). Both are decoded in `AgentLedger`. **FakeLedger-vs-canister faithfulness (W3 audit, verified):** `FakeLedger.pay` mirrors the canister's hard rejects — self-transfer (`from==to`) and pay-to-mint-sentinel (`to==[0xFF;32]`) are rejected exactly as the canister does (pinned by `w3_fakeledger_rejects_*` relay tests); the faucet amount/cooldown divergence is documented (FakeLedger is the permissive demo model). Accepted simplification: FakeLedger has no fee model (the canister checks `amount+fee<=balance`; FakeLedger checks `amount<=balance`) — it is the fee-less demo ledger, the real canister+ledger enforce fees authoritatively.
- **Durable transaction history is ledger-sourced-of-effect, locally indexed.** The facade appends every settled payment to a per-(account, currency) stable-memory index (`ACCOUNT_TXNS`, key = `pubkey|currency|seq_be`, stored under both `from` and `to`) and exposes `transactions_of(blob, nat32, nat32) -> vec` (newest-first, survives upgrades). `mint`/`burn` are recorded too (counterparty = the `MINT_ACCOUNT` sentinel). The query path uses `StableBTreeMap::range(..).rev().take(limit)` — O(limit), not O(total) — which matters because the wallet polls it every 5s.
- **The deposit/top-up surface reuses the exact account model — by construction, not coincidence.** The ckBTC-style deposit proxy (`deposit_address` / `refresh_deposit` / `deposit_info` + admin `register_minter`) calls the ck minter with `owner = canister_self()`, `subaccount = pubkey`, so a confirmed mint lands at the very `Account` `pay`/`balance_of`/`transactions_of` already read. Zero settlement/balance/history code changed — the deposit feature is a pure informational+orchestration layer on the facade, and a deposit that confirms is *automatically* the next balance poll's number. The relay surfaces it symmetrically: three new `Ledger` trait methods (`deposit_address` / `deposit_status` / `deposit_info`, `ledger.rs:167`) and three REST routes (`GET /api/v1/deposit/address/{hex}`, `POST /api/v1/deposit/refresh/{hex}`, `GET /api/v1/deposit/info`, `app.rs:122`). Per the plan's §0 error rule the proxy has **no permanent-policy failure** (no sig/cap/replay), so all three map any `LedgerError` → HTTP **503** — there is deliberately no `422` path (contrast `pay`/`faucet`, which keep `Rejected`→422). `FakeLedger` simulates the mint with a `pending_deposits` map + a `register_deposit` test hook (drain-and-credit on `deposit_status`); `AgentLedger` proxies the facade and normalizes the minter's candid `Nat` block index to a JSON-safe `String`. The relay layer is covered by unit tests (`tests/relay.rs`: address determinism, `deposit_status` drains+credits, and the HTTP route).

## A radical e2e harness drives the REAL app (18 flows; supersedes the old ui/ harness)

`e2e/` (its own npm package) is the flow-verifier the project was missing — it renders the **real** `app/App.tsx` (unmodified) in `react-native-web` + headless chrome, against the **real** test relay (FakeLedger, offline), and drives the wallet through real UI flows. It is NOT a parallel-component harness (the old `ui/` rendered `ui/src/App.jsx`; **`ui/` is now deleted** — `e2e/` drives the real app AND screenshots every flow state into `e2e/shots/`, so the golden-shot function is fully migrated). Every line of the app's TS — `payments.ts`, the wallet state machine, the fetch calls — runs verbatim. Only the I/O boundary is shimmed:

- **`DpayCore` signing shim (CRITICAL — byte-exact):** `e2e/web/dpay-core.ts` implements Ed25519 sign/verify/encode/decode over `@noble/ed25519`, reading field offsets/lengths/endian from `dfx/wire_layout.json` (the single source of truth, generated by `cargo run -p dpay-fixture --release -- wire-layout`). `e2e/tests/00-cross-val.mjs` re-signs the golden Authorization with the shim and asserts byte-identical sig + wire to the Rust core, proving local pay flows will settle on the real FakeLedger (which calls `sa.verify()`). The shim is installed into `react-native-web`'s `NativeModules.DpayCore`, so the app reads it via the **same** `const {DpayCore} = NativeModules` seam as on-device. (`e2e/harness/wire.mjs` exposes the same pure byte builders + signing Node-side, so flows 06/07/09/10 build/decode requests + sign authorizations with the real key without re-deriving the math.)
- **Camera scan** — `react-native-vision-camera` stub; `useCodeScanner` fans `window.__DPAY_TEST_SCAN(<string>)` to the app's `onCodeScanned` (smallest boundary — the app's downstream decode/submit logic runs unchanged). The hook registers its listener in a `useEffect` and removes it on unmount (cleanup contract — verified by flow 17; an earlier version leaked one listener per render). Flows 07/08/10 inject a request/signed QR this way; `window.__DPAY_TEST_SCAN_COUNT()` exposes the live listener count for the cleanup assertion.
- **DpayNfc + NFC session seam (WIRED to the real bus, audited):** the native-module surface is a no-op stub, and `window.__DPAY_TEST_NFC_SESSION(event)` emits `DpayNfcEvent`s through a `react-native-web` `NativeEventEmitter` instance — i.e. the SAME global `RCTDeviceEventEmitter` bus the app's `new NativeEventEmitter(DpayNfc).addListener('DpayNfcEvent', …)` listens on (an earlier scaffold used a private registry that never reached the app). **Audit (verified, not a shortcut):** RNW's `RCTDeviceEventEmitter` is a single module-level singleton (`export default new EventEmitter()` — one instance in the built bundle), and `NativeEventEmitter.addListener`/`emit` BOTH delegate to that exact singleton (`addListener`→`RCTDeviceEventEmitter.addListener`, `emit`→`RCTDeviceEventEmitter.emit`), keyed by event name; the `_nativeModule` arg only drives the `addListener`/`removeListeners` lifecycle callbacks (no-ops in the shim), NOT event routing. The suite runs tests in a BOUNDED PARALLEL pool (`run.mjs`; `DPAY_E2E_CONCURRENCY=N`, default 10 — the measured sweet spot on a 16-core host; `1` = sequential for debugging; `DPAY_E2E_FILTER=NN` runs a subset for fast per-test TDD): full suite ~13s for 18 real-browser flows (warn threshold 15s). **Concurrency-safety proof:** FakeLedger holds ALL state (balances, spent nonces, txns, pending deposits) behind ONE `Mutex<FakeState>` (`ledger.rs`) and the relay's idempotency cache is `Arc<Mutex<HashMap>>`, so concurrent requests serialize on the lock; each test onboards a DISTINCT random 32-byte pubkey → distinct `(pubkey, currency)` balance keys → no collision, and each payment nonce is a random 16-byte value → collision-free; reads are account-scoped; screenshots use distinct filenames. So N parallel contexts against the one relay touch DISJOINT account/nonce keys — parallelism changes no assertion and adds no coupling. Fail-fast: the first RED test stops new tests from STARTING (in-flight drain + "(not run — fail-fast)" markers, then non-zero exit). **E2e relay binary isolation (root fix for the always-rebuild workaround):** the e2e relay MUST carry `--features test-helpers` (the `/api/v1/test/deposit/seed` route), but `just check`/`just test-relay` build the SAME crate WITHOUT the feature into the SHARED `target/debug/dpay-relay` → clobber. The harness builds its relay into a DEDICATED `.dev/target-e2e` (gitignored; deps cache shared via `.dev/cargo`) so nothing else writes the e2e binary — and the harness ALWAYS invokes `cargo build` there (a warm no-op is ~0.3s) so cargo's fingerprinting is AUTHORITATIVE — a relay SOURCE edit (R1/R2/…) reliably produces a fresh binary. (An earlier `existsSync` build-if-missing gate skipped cargo when the binary existed, so a source edit left a STALE binary — e.g. a pre-receipt-signing relay kept running after R2, failing the app's receipt verification; letting cargo run every time is the true fix.) `just e2e` is clobber-immune after `just check`. A post-spawn stateless probe (POST `/test/deposit/seed` with a 4-byte account → `400`, never touching the ledger) is a SAFETY NET that force-rebuilds once if the route ever 404s. `just verify = check e2e` (the old `ui` recipe is gone).


## Stable-memory layout (upgrade compatibility)

State lives in stable structures so it survives upgrades automatically (no `pre_upgrade`/`post_upgrade`). The facade preserves the pre-facade shipping canister's `SPENT` (MemoryId 1, value `()` — a set), `CAP` (2), `TXN_SEQ` (3), and `ACCOUNT_TXNS` (4) at the **same** MemoryIds/types, so an in-place upgrade of `ssqti` keeps nonces + history. The legacy internal `BALANCES` (MemoryId 0) is abandoned-and-inert (orphaned play money; unread by the facade). New facade state uses fresh MemoryIds: `LEDGERS` (5), `CONTROLLER` (6), `BAL_CACHE` (7), `MINTERS` (8), `FAUCET_COOLDOWN` (9 — `(currency,pubkey)`→last-faucet secs, backs the self-service faucet rate-limit; value type `u64`, key reuses `CacheKey`), `RECEIPT_SECRET` (10 — the canister's receipt Ed25519 secret, `Option<[u8;32]>` in a `StableCell`; generated once via `raw_rand`, never rotated), `RECEIPTS` (11 — `nonce`→`StoredReceipt`{canonical claim bytes[108]+sig[64]}, backs `receipt(nonce)`), `WITHDRAW_NONCES` (12 — `nonce`→`()`, the withdrawal idempotency set; a SEPARATE map from `SPENT` so a withdraw nonce can't collide with/block a pay nonce, mirroring `SPENT`'s reserve/release/settle semantics for the `withdraw` path), `CURRENCY_META` (13 — `currency`→`CurrencyMetaStorable`{opt symbol + opt decimals + opt minter_family byte}; backs the `currencies()` catalog + `MinterFamily` ramp-dispatch key, M0). `MINTERS`'s value is the `PrincipalStorable` newtype (raw ≤29 principal bytes; `BOUND = Bounded{29, is_fixed_size:false}`) — a separate map so the existing `LedgerEntry{principal, mintable}` encoding on MemoryId 5 is untouched. NB: `SPENT` keeps value type `()` rather than a 1-byte Pending/Settled enum — reusing a MemoryId with a different value size would corrupt the B-tree on upgrade, and `contains_key` (the sole read) makes the set semantically equivalent. The MemoryId/type compatibility (1–4 reused with identical key/value layout; 5/6/7/8/9/13 on fresh MemoryIds; 0 abandoned-and-inert) is **verified by inspection** of the `thread_local!` block — it is not proven by a cross-version test. The regression test `upgrade_preserves_nonces_and_history` covers **stable-structure survival across an upgrade round-trip**, but note it upgrades facade → *same*-facade wasm, so it proves the stable-structure round-trip, NOT the real old-internal-canister → facade layout. TODO: a true old-wasm → facade cross-version test would be stronger, but the old internal-canister crate is deleted, so its wasm isn't readily available.

## Risks worth flagging before a coding session

**1. Canister controller is unaddressed in code.** 🟡 **NARROWED (R4).** `CLAUDE.md` calls this load-bearing ("whoever can upgrade can set fee=100%"). The **code now supports a governed controller end-to-end** (R1): admin methods are denied when `controller == null` (open default closed), `InitArg.controller` seeds a governed principal at deploy, and `set_controller` is two-step rotation (a locked canister only rotates via its controller) — see `docs/GOVERNANCE.md` for the exact operator steps to seed the in-canister controller AND hand the IC-level code controller to an SNS root / blackhole. The remaining piece is the **external, human step**: actually performing that hand-off at deploy (it cannot be faked in code, and is deliberately not done in this repo). Until it lands, "we can't touch your funds" is a promise, not a property. (Distinct layers: the in-canister `CONTROLLER` gates admin *methods*; the IC-level code controller gates *upgrades* — both must be governed. `provision_ledger_canister`/`transfer_cycles` remain on the fixed `ADMIN_CALLERS` operator allowlist — rotate before production.)

**2. `mint`/`burn`/`register_ledger`/`register_minter` are open when no governance controller is set.** ✅ **RESOLVED (R1).** The privileged admin ops are now **denied when `controller == null`** (`require_admin` flips from open-when-null to denied-when-null): a deployment that forgets to seed a governed controller cannot have its currency repointed or its demo currency printed by any caller. The demo's self-service on-ramp is now a **separate `faucet(account, currency)` method** that mints a FIXED constants-sourced amount (`FAUCET_AMOUNT = 10_000` = $100.00) and is **rate-limited per (account, currency)** via the stable `FAUCET_COOLDOWN` map (MemoryId 9, one mint per `FAUCET_COOLDOWN_SECS` = 1h window) — no admin gate. The relay's `/faucet` route calls `Ledger::faucet` (the `Ledger::mint` trait method is gone: the relay has no admin-mint path, it is not the controller). The faucet mints the fixed amount regardless of what a client asks (the canister ignores the requested `amount`; the permissive `FakeLedger` honors it as play money for the offline demo — a documented divergence). Proven on PocketIC: `open_mode_denies_admin_but_faucet_and_lockdown_work`, `controller_rotation_is_two_step`, `faucet_mints_fixed_amount_and_rate_limits`. `set_controller` keeps a one-time open-mode lockdown (callable when null) + two-step rotation once locked; the production path is to seed a governed principal at `init` (see risk 1 / docs/GOVERNANCE.md). (`provision_ledger_canister` and `transfer_cycles` remain separately gated by the fixed `ADMIN_CALLERS` operator allowlist — rotate to an SNS/governance principal before production.)

**3. Receipt is unsigned.** ✅ **RESOLVED (R2).** The canister now signs a canonical **outcome receipt** with a canister-local **Ed25519** keypair (the payer's sig already bound the terms; the receipt sig binds the OUTCOME). The secret half lives in stable memory (`RECEIPT_SECRET`, MemoryId 10), generated once from `management_canister::raw_rand` (strong consensus entropy, not a PRNG seed) on first successful `pay` (or eagerly via `init_receipt_key`); the public half is exposed via `receipt_pubkey()`. `pay()` signs `ReceiptClaim{nonce, from, to, amount, currency, block_index, settle_ts}` (FROZEN 108-byte LE canonical layout, single-sourced in `dpay_core::ReceiptClaim::signing_bytes`) and returns the sig + pubkey + claim fields in `PayReceipt`; `receipt(nonce)` returns the stored signed receipt for replay/reconciliation. The relay's `Receipt` carries the sig/pubkey/claim through (`/pay` + `/receipt/:nonce`); the app verifies the sig (FFI `verify_receipt_sig` on device via the Rust core; `@noble/ed25519` in the e2e shim) before showing "Paid ✓" — a merchant/relay cannot forge the outcome. Proven on PocketIC: `pay_yields_canister_signed_verifiable_receipt` (verify / tamper-fails / replay-returns-same-receipt); relay `pay_returns_signed_receipt_that_verifies`; e2e 15/15 with the app verifying. **Documented follow-up (stronger, not attempted):** IC chain-key `sign_with_schnorr`/`sign_with_ecdsa` so the key never lives in stable memory — the current Ed25519-in-stable model is canister-controlled (only the canister signs, defeating the actual lying-merchant threat) and uniform with the app's existing Ed25519 verify, but a chain-key threshold signature would remove the stable-key exposure entirely.

**4. Cross-canister trap window (residual, mitigated).** ✅ **RESOLVED (R3, bounded).** If the canister traps between the ledger committing `Ok` and `settle_nonce` completing, the IC rolls back this canister's message (including the SPENT nonce reservation) while the ledger's debit persists. Mitigated by the quantized `created_at_time` dedup (same-bucket retry → ledger `Duplicate`), and now **closed airtight by an admin-gated `reconcile(currency)`** (controller-only): it walks the currency's recent ledger transactions (typed `get_transactions`, `RECONCILE_MAX_BLOCKS`=10k window), matches each facade-account debit (a `transfer` with `from.owner == canister_self`, `from.subaccount == Some(pk)`, and a 16-byte nonce `memo`) to a SPENT entry, and repairs the orphans (marks the nonce spent + records the txn + refreshes the display cache) so a post-trap retry is correctly treated as a duplicate. Idempotent on consistent state. Proven on PocketIC with a `reinstall_canister`-based trap simulation (the reinstall wipes the facade's stable SPENT while the ledger keeps its debit — exactly the post-trap rollback state): `trap_window_lets_a_retry_double_debit_without_reconcile` (the bug — a cross-bucket retry double-debits) and `reconcile_repairs_trap_orphan_and_blocks_double_debit` (the close — reconcile repairs the orphan, a retry is rejected, no second debit; idempotent; admin-gated). **Bounded scope (documented):** single-currency, recent in-canister blocks (archived ranges are not paged); the trigger is admin-invoked (a heartbeat auto-trigger is a documented follow-up — it is a cycle-cost/operations tradeoff, not a correctness gap, since the quantized-dedup mitigation already narrows the window to >60s cross-bucket retries and the operator can run `reconcile` after any suspected trap or on a schedule). The dominant realistic trap source remains stable-memory exhaustion in `record_txn`.

**5. `opt-level=1` in dev profile.** Speeds the inner loop but means proptest counterexamples run under light optimization — fine, just don't debug release-only miscompiles here.

**6. Transaction history is unbounded + single-page only (production roadmap).** Every settled payment writes two `TxnRecord`s, ~144B each, with no pruning and no cursor — a long-lived wallet grows without bound and can only fetch the newest ≤100 rows. Acceptable for the PoC/demo; before a pilot the history needs a paginated cursor, a retention window, or off-canister indexing. Not a correctness or money-safety issue (records are write-only-after-settle and never gate settlement).

**7. Deposit-proxy endpoints are unauthenticated (acceptable; documented).** `deposit_address` / `refresh_deposit` / `deposit_info` carry no caller gate — by design (plan §0): a deposit address is not secret (revealing it only lets someone send *to* the user), the minter methods are themselves permissionless (GeneralAvailability on mainnet; `get_minter_info` confirms no KYC checker — only automatic KYT that screens tainted UTXOs, not principals), and `refresh_deposit` — the only value-creating one — is idempotent and a no-op when no UTXOs have confirmed (anyone triggering a real mint only credits the named pubkey). This is the right posture, with one operational invariant to keep: a ck currency MUST have its minter `register_minter`'d at deploy — an unregistered minter surfaces as `Err("currency N has no ck minter")` → relay `Transient` → **503** (a deploy-time config invariant, not a runtime money risk). **Multi-currency catalog (M0, closes the old `DEPOSIT_CURRENCY=1` single-sourcing issue):** a new unauthenticated `currencies() -> Vec<CurrencyDescriptor>` query joins `LEDGERS` + `MINTERS` + a new `CURRENCY_META` map (MemoryId 13; admin-gated `register_currency_meta` sets `symbol`/`decimals`/`minter_family`), and the relay surfaces it at `GET /api/v1/currencies`; the app now fetches + caches the catalog and resolves currency ids at runtime instead of hardcoding them. Adding a currency = canister config-only (no app redeploy). `MinterFamily = {CkBtcUtxo, CkEthErc20, CkSol}` drives per-family ramp dispatch. ckETH/ckERC20 deposits reuse the proxy seam but need a DIFFERENT deposit path (Ethereum helper-contract call, no per-principal IC address, no user-callable mint) — that ramp dispatch is **not built**; the C-MOCK calldata builder (`app/cketh.ts`, byte-exact goldens) and verified live params (O6) are the foundation. The withdrawal path (`withdraw`) is DISTINCT: it carries a verified user Ed25519 signature (the non-custodial gate) — unauthenticated withdrawal would let anyone drain a subaccount.

**8. Withdrawal approve→retrieve front-running (residual, inherent).** 🟡 `withdraw` calls `icrc2_approve` then `retrieve_btc_with_approval` across an `await`; a separate caller could in principle front-run the facade's retrieve with an attacker address, consuming the single-use allowance. Blast radius is bounded to the EXACT authorized `amount` (the approval is for that amount, consumed once) — never the user's whole balance — and the facade's own retrieve follows immediately. This is the documented ckBTC-withdrawal residual every `retrieve_btc_with_approval` client carries (the minter offers no signature-binding-the-destination path); it is NOT a dpay-specific gap. No code fix is possible without a minter change; documented here so it is a known, bounded property, not a silent one.

> **Offline proof status — RESOLVED.** The deposit surface is proven end-to-end offline on PocketIC through the real facade. A test-only **mock-minter** canister exists at `crates/dpay-mock-minter/` (a workspace member; builds clean with `-D warnings`, zero warnings; never shipped to mainnet) — it reimplements the ckBTC minter's six methods (`get_btc_address` / `update_balance` / `register_deposit` / `get_minter_info` / `get_deposit_fee` / `get_known_utxos`) and mints onto a real `ic-icrc1-ledger` from the ledger's minting account. The mock's candid surface **exactly mirrors the REAL ckBTC minter** (`get_btc_address` / `update_balance` / `get_known_utxos` each take ONE record argument `{ owner: opt principal; subaccount: opt blob }`, verified against `dfx canister metadata mqygn-kiaaa-aaaar-qaadq-cai candid:service --network ic`) — this is load-bearing: an earlier mock agreed with a broken facade on the WRONG two-positional-arg contract, so PocketIC never caught the divergence and the live `get_btc_address`/`update_balance` TRAPPED on mainnet with `IC0503 ... Fail to decode argument 0 ... Subtyping error: Type mismatch`. The fix: the facade now encodes the call as a candid **1-tuple** `(MinterAccount{ owner, subaccount },)` (ONE record argument) via `with_args`, and the mock takes the same single record arg (`AccountArg`). The proof lives at `crates/dpay-canister-tests/tests/deposit.rs` and `just test-canister` is **GREEN: 25/25** (22 `icrc_settle` + 3 deposit). The deposit test asserts: `deposit_address` → `register_deposit` (seed) → `refresh_deposit` → **the mint lands at `Account{owner: facade, subaccount: pubkey}` where `icrc1_balance_of` reads (balance grew)** → a second refresh is empty (drained, no double-mint) → `deposit_info` correct. A closed-loop test proves the minted ckBTC is immediately spendable via the unchanged `pay` path (deposit → refresh → offline-signed pay → the ledger reflects the move). A direct **honesty-guard test** (`mock_minter_enforces_real_minter_single_record_arg_contract`) drives the mock with BOTH the single-record shape (succeeds) and the divergent two-positional-arg shape (rejected with the real-minter decode trap) — so if either the facade OR the mock ever revert to the 2-tuple encoding, a test fails exactly as it did on mainnet.

## ckUSDC onramp/offramp — multi-currency foundation laid, ramp dispatch pending

The ckBTC-shaped deposit/withdraw proxy does NOT generalize to ckUSDC. ckUSDC is a **ckERC-20** handled by the **ckETH minter** (`sv3dd-…`), against the ckUSDC ledger (`xevnm-…`, 6 decimals). Its onramp has **no per-principal IC address and no user-callable mint** — the user performs two Ethereum transactions from their OWN wallet (`approve(helper,amount)` on USDC ERC-20 + `depositErc20(erc20,amount,principalAsBytes32,subaccount)` on the helper contract); the minter scrapes ETH logs on a ~3min heartbeat and mints to `(principal, subaccount)` (~20min total). Three minter families exist (`CkBtcUtxo`/`CkEthErc20`/`CkSol`), so the right design is per-family ramp dispatch keyed off `minter_family`, not "generalize the ckBTC proxy".

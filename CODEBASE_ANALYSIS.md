## Architecture health: strong

The single most load-bearing decision — **one Rust core shared by every consumer** — is actually enforced everywhere:

- `dpay-core` (`lib.rs` + the `nfc/` module directory, split 2026-08-11 from a 1749-line `nfc.rs` and grown since — read the directory rather than a list here) is the source of truth for signing, validation, codec, NFC framing, and — since 2026-09-04 (`0e206dc`) — the merchant's till ring-up (`TillOpen` / `sign_till_open` / `validate_till_open`, domain-separated `dpay-till-open-v1`), which is a fourth signing surface over the same device key. The canister, relay, sim, fixture, and FFI all import it; the app reaches it via UniFFI → `libdpay_ffi.so`. There is no parallel JS/Kotlin reimplementation of money logic. The IC user-principal rail extends the same discipline: `crates/dpay-icp` (pure-Rust principal derivation, `request_id` hashing, ed25519 envelope signing, CBOR emission rules, hand-rolled ICRC-1/2 DIDL codecs — transport-free/HTTP-free/clock-free, wasm32-safe, deps only `ed25519-dalek`+`sha2`, goldens byte-identical to the production `ic-agent`/`candid` crates) is the ONLY envelope implementation, consumed by the app via FFI (`icp_*`) and by the web wallet via the wasm core (`w_icp_*`).
- **Current IC NFC architecture is protocol v2 (2026-08-21 offline-payer fix).** The online merchant puts a certified IC expiry in the 132-byte request. The payer performs no network call: it signs the ICRC update plus a reusable sender-authorized read_state envelope and serves both in a DPN2 bundle. The merchant is the single settlement owner: submit exact update bytes, poll with the payer-signed capability, require exact history before claiming settlement, then Ed25519-sign `{status, nonce, request_id}` and return it over result APDU C6. The card verifies that signature against `PaymentRequest.to`. Since read_state trees are structurally decoded but not BLS-verified, a rejection without the exact row is signed as unknown, not declined. `AwaitingResult` supports arbitrarily delayed result-only re-taps; expiry blocks new taps but preserves an active settlement; JS generations, native reader identities, request IDs, and payer request nonces prevent stale sessions mutating replacements; `Complete` sessions never replay a bundle. After confirmation, the merchant intentionally retains Android reader mode until the terminal UI unmounts: eager `disableReaderMode` while the phones remain coupled makes Android rediscover the payer as a generic tag and display an unrelated app chooser. Reader mode is Activity-scoped, so an OEM system Activity taking foreground can still suspend it; a USB-connected physical test must not be treated as representative if USB Settings interrupts the tap. HTTP status alone cannot decline, and SOL's independent receipt protocol is untouched.
- **Historical marker:** the next two envelope-only/request-status bullets record the first 2026-08-21 rewrite and are superseded by protocol v2 above. They remain only to explain why the online-payer-only design was replaced.
- **IC NFC is now a minimal signed-envelope handoff (2026-08-21 field-failure rewrite).** The old request→wire→wait-online→17-byte-receipt protocol duplicated settlement ownership across Rust, Kotlin, `useNfcTapState`, `NfcTap`, and `ReceiveMode`; it produced three contradictory verdicts for one settled physical tap. The receipt APDU/state/FFI/bridge APIs and native 12-second rendezvous are deleted. NFC terminates when the immutable signed envelope is delivered; completed card sessions reject re-selection and native clears both roles immediately. Both phones may submit identical bytes safely by IC request-ID dedup, but settlement authorization is deliberately asymmetric: only the payer may poll its request_status, while the receiver confirms exact `{recipient,currency,amount,memo nonce}` in durable ICRC-3 history. HTTP status alone never creates a decline; `Duplicate{duplicate_of}` is settled, and only sender-authorized read_state plus a decoded non-Duplicate ledger error rejects. `ReceiveMode.tapHandoff`/`nfc-reconcile` and receiver-signed request-ID polling are deleted. SOL keeps its separate receipt protocol and receipt wait.
- **IC request-status authorization is sender-bound.** `submitTransfer` is payer/offramp-side only and always polls after the POST, including 4xx/429, because one peer's HTTP response cannot override an identical envelope already submitted by the other. Merchant NFC, signed-QR, and proof hand-back all reuse `confirmIncomingTransfer`: the relay's read-only ICRC-3 history must contain the open request's exact recipient, currency, raw amount, and random 16-byte memo before any `Received` UI is allowed.
- **Superseded historical record:** the next bullet documents the deleted receipt/handoff design and is retained only to explain why it failed; it is not current architecture.
- **Outcome classification is pure, single-sourced, and never signature math.** `RailOutcome` (settled / rejected / unknown) is declared and decided in `app/services/rail.ts` and jest-pinned by `app/__tests__/rail.test.ts`; SOL keeps its own independent receipt constants in `app/solana/payments.ts`. The load-bearing rule is that an unverifiable answer is NEVER promoted to a decline — what a merchant may claim about a tap, and why there are exactly three verdicts rather than one collapsed "pending", is stated once in the `MerchantVerdict` doc comment in `app/components/NfcTap.tsx`; the poll budgets that bound it are the two consts at the top of that same file. Offline coverage of the window that motivated it (mainnet latency outrunning the in-tap budget — the "Confirming… → failed" field bug, 2026-08-21): the fake-IC gateway settles SYNCHRONOUSLY, so that window structurally cannot occur offline and the seam is opened deliberately — test-helpers `POST /api/v1/test/hide_outcome` `{request_id, polls}` omits ONE rid's `request_status` entry from the next N read_state certs (`FakeIc::hidden_outcomes`, `crates/dpay-relay/src/app.rs`), reproducing boundary-node outcome latency without disturbing concurrent flows; e2e flow 86 drives the recovery. `rail.test.ts` pins `st==null`/`state:'done'` → `{kind:'unknown'}` (never a false decline), and `fmtTime` guards non-finite/ns timestamps to `'—'`.
- **The user-principal IC rail is the value path (2026-08-19/20 cutover, "W1–W8").** Funds live at `Account{owner: <self-authenticating(device ed25519 pubkey)>, subaccount: None}` directly on the external ICRC ledgers; the app signs `/api/v2` envelopes locally and submits them to the boundary nodes (`icp-api.io` in prod — the relay's `test-helpers` fake-IC gateway in tests). The facade and relay are OUT of the value path (see the dedicated section near the end). Load-bearing invariants, all in `app/services/icp.ts` + `app/services/rail.ts`: retry is **identical-byte resubmit ONLY** (re-signing = new `request_id` = double-pay — nothing re-signs a submitted envelope); `icSubmit` classifies 3-way (`accepted` → poll `read_state`; `rejected` = definitive 4xx; `unknown` = 5xx/timeout → honest pending); value envelopes are stamped via the **certified IC clock** (`icStampExpiry` throws on unreachable/skewed time — never sign on a bad clock; polls fall back to device time since they can't affect correctness). **read_state routing constraint (2026-08-21 fix, found via a two-physical-phone NFC decline):** the certified-clock sync (`icNowNs`) routes its `[[time]]` read_state at `IC_TIME_ROUTING_CANISTER` = the prod DUSD ledger (`td2nx…`) — NOT the management canister. icp-api.io only routes read_state to registered canister ids (`aaaaa-aa` → 400 `canister_not_found`, measured 3/3), so the old target made `icNowNs` deterministically null on prod → `icStampExpiry` threw "IC clock unreachable" → the NFC payer's autoSign catch auto-declined → merchant saw sticky 6985 "payment was declined" while balances kept working (poll fallback) and the offline suites stayed green (the fake gateway skips canister-known validation for read_state; the mainnet Rust e2e polls read_state only against real target canisters) — a textbook prod-only blind spot. The time leaf is in every subnet's certified tree, so any routable canister works; if the routing target ever changes, it must be a registered prod canister.
- **The RN app is modular, not monolithic** (`app/App.tsx`, split 2026-07-31 — plan: `docs/specs/2026-07-31-app-split-plan.md`). The root only loads identity + relay, runs the self-check, and routes `Onboarding | Wallet`; everything else lives behind a strictly-layered module tree — `config/` (palette + theme, constants incl. `POLL`, the bundled currency catalog, and `assets.ts`, which owns `buildSelectableAssets`/`resolvePayLink`), `lib/` (types + pure format/amount/ledger helpers + the clipboard, deep-link, destination-classifier and scanner utilities), `hooks/` (TRUE React hooks — the Wallet data hooks `useCatalog`/`useBalancePoll`/`useTransactionHistory`, their SOL counterparts, and the shared NFC tap state machine `useNfcTapState`), `services/` (the single `NativeModules.DpayCore/DpayNfc/DpaySolNfc` destructure plus the IC-rail clients — `icp.ts` the `/api/v2` transport and `rail.ts` the ONE build/sign/submit/poll implementation behind PayMode/NfcTap/WithdrawSheet/SendSheet — the residual relay fetch clients, the OpenCryptoPay payer and till clients, and the persistence wrappers), `i18n/` (four locales behind `M`), `solana/` (the app-scoped native SOL rail), `styles.ts` (ONE style vocabulary as a palette-parameterized `buildStyles(p)` behind the mutable `S` holder), and `components/`. **The file list is deliberately NOT enumerated here** — the enumeration that used to sit in this bullet drifted 29 components out of date, and a prose copy of `ls` will always lose to the directory. Read the directories, and read each module's own header comment for its rules. Dependency direction is acyclic: `lib/config` are leaves → `hooks/services` → `components` → `App.tsx`; no production module imports `Wallet` except `App.tsx`, and only `App.tsx` consumes `./relayConfig` (so the e2e `?relay=` override keeps applying) — `relayUrl` is threaded as a prop everywhere else. **Rail selection is DERIVED, not toggled** (`252c2af`, 2026-08-08): `Wallet` owns exactly one `selectedAssetId`, and `selectedAsset.protocol === 'solana'` is what picks `SolPayMode` over `PayMode` — the old `[ IC | SOL ]` `RailSelector` is deleted, and its `railRow`/`railPill` styles are repurposed for `ModeToggle`. **Send/Receive IA (2026-08-09, `f882a04`):** on-chain Send/Receive live in the Pay/Receive tabs, not on Balances rows — `ReceiveMode` carries a `[ Request payment | My address ]` toggle and `PayMode` a `[ Scan to pay | Send to address ]` one, with Wallet owning the within-tab sub-mode state so deeplinks land the user directly on the right surface. `BalancesSheet` is a pure balance-list + select screen: each row is ONE whole-row `Pressable` (`testID="asset-<key>-select"`, container `asset-<key>` for textContent reads) wrapping row + subtitle + children via `assetSelectBlock`, so anywhere on the card body selects, while the DEMO faucet `actions` stay a row SIBLING — never nested, because RN-web renders Pressables as `<button>` and HTML forbids nested buttons; the brand left-border is active-ONLY (`assetCardActive`). DEMO hides the toggle (no on-chain family).

The wire format is frozen and byte-precise (`SIGNING_LEN=196`, `WIRE_LEN=292`, `REQUEST_LEN=132`), and `validate()` is pure/allocation-free — exactly what a canister hot path wants. Field order is documented as FROZEN, which is the right discipline for a protocol surface. **Post-cutover role:** the 292-byte signed authorization is no longer the payment wire — the app signs full IC `/api/v2` envelopes (~390 bytes; NFC framing is payload-length-agnostic and still carries it in 2 frames) — but the frozen codec is NOT dead surface: the 132-byte request QR is unchanged, the NFC transport + wasm exports still speak it, and the canister kernel (dormant) still settles it.

**Wire-format v2 (2026-07-31): names + memo are now authenticated display hints.** `from_name`/`to_name`/`memo` (32 B each, UTF-8 trailing-NUL-padded) live INSIDE `Authorization::signing_bytes`; `to_name` + `memo` also ride the `PaymentRequest` (merchant-defined; the payer copies them verbatim like `amount`). The signature binds them, so a relay/merchant cannot swap a name or memo after signing — they flow: payer signs → canister `TxnRecord` (196 B fixed, the same layout as the signing bytes) → relay history → the app renders friendly counterparties ("from Alice" / "to Bob" + memo) instead of raw hex. Names are self-chosen and NON-UNIQUE — they are a display hint, NOT an identity (the pubkey is still the identity, still in the bytes). Mint-sentinel history rows use empty names; the app special-cases `MINT_HEX` so faucet rows render as "Demo funds" rather than `ffffffff…`. The old out-of-band `|name` QR suffix is DELETED (the name now lives in the request bytes — single source of truth). `ReceiptClaim` (108 B canonical outcome layout) and `WithdrawAuth` are UNCHANGED. Closes N6 + H3 (see `OPEN_ISSUES.md`).

Every currency = one real ICRC ledger canister (the DFINITY `ic-icrc1-ledger`); the facade routes every payment through this one interface.

PLUS a **deposit-proxy surface** (ckBTC-style top-up) — four `#[update]` endpoints that proxy an external chain-key minter so the wallet can show a per-account native deposit address, poll for a confirmed mint, and read static deposit instructions: `deposit_address` / `refresh_deposit` / `deposit_info` (no auth — see risk 7). ~~plus `register_minter` (admin-gated by the same `require_admin` controller as `register_ledger`). The minter principal per currency lives in a separate stable map `MINTERS` (`MemoryId 8`; value = `PrincipalStorable`, a principal newtype that serializes the raw ≤29 bytes with no present-flag — absence is expressed by map membership).~~ — **removed with the registry (2026-08-28)**: the minter principal per currency is a compile-time const in the `FIXED_ASSETS` table (`types.rs`); the `MINTERS` stable map (MemoryId 8) is orphaned and never read. **KEY INVARIANT:** the minter is always called with `owner = Some(canister_self())`, `subaccount = Some(pubkey)` (`minter_call_btc_address` / `minter_call_update_balance`, lib.rs), so the mint lands on the currency's ICRC ledger at exactly `Account{owner: facade, subaccount: pubkey}` — the *same* account `account_of` (lib.rs:578) hands to `icrc1_balance_of` / `pay` / `transactions_of`. **Subtle encoding requirement (load-bearing):** the REAL ckBTC minter (`mqygn-kiaaa-aaaar-qaadq-cai`, verified via `dfx canister metadata … candid:service --network ic`) takes exactly ONE record argument `(record { owner: opt principal; subaccount: opt blob })` for `get_btc_address` / `update_balance`. The facade encodes this as a candid **1-tuple** `(MinterAccount{ owner, subaccount },)` passed via `Call::with_args(&arg)` — `with_args` on a 1-tuple emits ONE argument (the record). A 2-tuple `(Option<Principal>, Option<Vec<u8>>)` would instead emit TWO positional args and the real minter TRAPS with `IC0503 ... Fail to decode argument 0 ... Subtyping error: Type mismatch` (this exact trap shipped to mainnet once; see below). The single/zero-arg minter proxies and all ledger calls are unaffected. This invariant is pinned by the PocketIC deposit test + a direct mock-contract honesty guard (see "Offline proof status" below). The deposit surface is therefore **purely informational + orchestration**: it changes nothing about settlement, balance, or history — once a mint confirms, the existing balance/history reads reflect it with no code change. dpay never holds the deposited BTC (the minter does the chain-key work and credits the ledger directly), so the non-custodial posture is intact.

**Money-safety rule (load-bearing):** `pay()` ALWAYS reads the AUTHORITATIVE ledger balance (`icrc1_balance_of`) before transferring. The cache is DISPLAY-ONLY — a stale cache (someone transferred directly on the ledger) can only make a shown number wrong, never cause a bad settlement. ## Where the design earns its keep

- **Consent model is sound.** `PaymentRequest` carries no `from`/sig; `to_authorization(from)` copies everything verbatim, so the payer's signature binds exact amount+payee+nonce+currency. The `request_id` doubling as the nonce was elegant on the facade rail; post-cutover it is the ICRC memo and the envelope's own request id is what makes a replay settle once (`dpay_core::PaymentRequest`).
- **Per-currency segregation is across *canisters*, the strongest no-swap guarantee.** Post-cutover a user pubkey maps to `Account{owner: <user principal>, subaccount: None}` on each ledger independently (facade-kernel era: `Account{owner: <facade>, subaccount: <pubkey>}` — the segregation argument is unchanged, only the owner moved). Funds in currency X physically cannot be drawn by a payment naming currency Y — they live on a different ledger canister. This is stronger than a per-currency map key inside one canister. Proven by `currencies_cannot_cross`.
- **Cross-canister atomicity + replay safety is handled honestly.** `pay()` spans `await`s (balance/fee/transfer), and the IC interleaves messages at await points. Proven by `concurrent_pay_same_nonce_settles_once` (the double-spend regression). ## Stable-memory layout (upgrade compatibility)

State lives in stable structures so it survives upgrades automatically (no `pre_upgrade`/`post_upgrade`). The facade preserves the pre-facade shipping canister's `SPENT` (MemoryId 1, value `()` — a set), `CAP` (2), `TXN_SEQ` (3), and `ACCOUNT_TXNS` (4) at the **same** MemoryIds/types, so an in-place upgrade of `ssqti` keeps nonces + history. The legacy internal `BALANCES` (MemoryId 0) is abandoned-and-inert (orphaned play money; unread by the facade). New facade state uses fresh MemoryIds: `LEDGERS` (5), `CONTROLLER` (6), `BAL_CACHE` (7), `MINTERS` (8 — ABANDONED with the 2026-08-28 registry removal, as is `RETIRED` (14); neither has a `thread_local!` and `PrincipalStorable` is gone), `FAUCET_COOLDOWN` (9 — `(currency,pubkey)`→last-faucet secs, backs the canister's own (now dormant-on-prod) self-service faucet rate-limit; the production cooldown since 2026-08-20 lives relay-side in `FaucetCooldown`; value type `u64`, key reuses `CacheKey`), `RECEIPT_SECRET` (10 — the canister's receipt Ed25519 secret, `Option<[u8;32]>` in a `StableCell`; generated once via `raw_rand`, never rotated), `RECEIPTS` (11 — `nonce`→`StoredReceipt`{canonical claim bytes[108]+sig[64]}, backs `receipt(nonce)`), `WITHDRAW_NONCES` (12 — `nonce`→`()`, the withdrawal idempotency set; a SEPARATE map from `SPENT` so a withdraw nonce can't collide with/block a pay nonce, mirroring `SPENT`'s reserve/release/settle semantics for the `withdraw` path), `CURRENCY_META` (13 — `currency`→`CurrencyMetaStorable`{opt symbol + opt decimals + opt minter_family byte}; ~~backs the `currencies()` catalog + `MinterFamily` ramp-dispatch key, M0~~ — orphaned since the 2026-08-28 registry removal: the `currencies()` catalog no longer exists and `MinterFamily` dispatch keys off compile-time consts). `MINTERS`'s value is the `PrincipalStorable` newtype (raw ≤29 principal bytes; `BOUND = Bounded{29, is_fixed_size:false}`) — a separate map so the existing `LedgerEntry{principal, mintable}` encoding on MemoryId 5 is untouched. NB: `SPENT` keeps value type `()` rather than a 1-byte Pending/Settled enum — reusing a MemoryId with a different value size would corrupt the B-tree on upgrade, and `contains_key` (the sole read) makes the set semantically equivalent. The MemoryId/type compatibility (1–4 reused with identical key/value layout; 5/6/7/8/9/13 on fresh MemoryIds; 0 abandoned-and-inert) is **verified by inspection** of the `thread_local!` block — it is not proven by a cross-version test. The regression test `upgrade_preserves_nonces_and_history` covers **stable-structure survival across an upgrade round-trip**, but note it upgrades facade → *same*-facade wasm, so it proves the stable-structure round-trip, NOT the real old-internal-canister → facade layout. ## OpenCryptoPay — dpay pays a till (2026-09-01/02), and serves one (2026-09-04)

Two halves of one standard, both app/relay-scoped: no canister, no facade, no change to the 132-byte wire. Design and every founder decision: `docs/specs/2026-09-02-merchant-side-plan.md`. - **Where the code is.** Payer half: `app/lib/opencryptopay.ts` (pure — LNURL bech32, the URI grammars, the refusal taxonomy) + `app/services/opencryptopay.ts` (the provider reads and the one-shot `/tx`), reached from `app/lib/scan.ts` after the rail codec refuses a scan. Provider half: `crates/dpay-relay/src/till.rs`, driven by `app/services/till.ts` + `app/components/TillCharge.tsx` (the counter, inside Receive ▸ Request payment on every asset). Each of those four module headers is the authority for its own half.
- **The routes are OFF by default.** The till's seven routes register only when `DPAY_ENABLE_TILL` is set, and the gate is at REGISTRATION (`crates/dpay-relay/src/app.rs`, at the till gate) — an unregistered path is refused by the router and no till code is reachable, so it is one code path rather than a live endpoint with a disabled branch. What production is actually serving: `OPEN_ISSUES.md`.
- **A ring-up is a fourth signing surface over the device key.** `dpay_core::validate_till_open` holds the whole acceptance rule and the relay calls it rather than re-deriving it; `TillStore::authorize` adds the two things a pure function cannot have (the seen-nonce set, and check-and-burn under one borrow).
- **The tap rides the existing IC rail unchanged.** The counter arms the reader with the charge's `reference` as the request nonce, which `prepareNfcTransfer` writes as the transfer's ICRC-1 memo — so a tap settles the same charge a scan would, with no new AID, no protocol change and no second crediting path. The merchant's tap verdict is a three-value union (`settled` / `refused-unverified` / `nothing-seen`, `NfcTap.tsx`): neither non-settled leg is rendered as a decline, because a `read_state` tree is decoded but not BLS-verified on the device.
- **Two trust decisions to know before touching this.** (1) A non-ICP Internet Computer asset is payable only at a till served by the relay this wallet is already configured to use — `isOwnRelayProvider`, compared against the TLS-attested host that answered rather than the host a provider claims; the refusal is `unverifiable-ic-asset`. It is knowingly incomplete the day a second merchant runs a relay. (2) `GET /api/v1/till/{id}` is unauthenticated and the charge id is a bearer read token, which is why the `reference` is served only to the merchant who signed the ring-up (`ChargeStatus`).
- **Who can pay a dpay till: a dpay wallet.** No wallet on the standard's own compatibility list settles any Internet Computer asset (measured twice — findings doc), so conformance is future-proofing, not distribution. The asymmetry runs the opposite way from dpay's own rail: an OpenCryptoPay payer must be online — the standard makes the payer fetch the quote, fetch the destination and report the proof over https — while a dpay payer can be offline over NFC or QR.

## Architecture health: strong

The single most load-bearing decision — **one Rust core shared by every consumer** — is actually enforced everywhere:

- `dpay-core` (`lib.rs` 454 lines + `nfc/` module directory: `mod.rs` + `apdu.rs` + `frame.rs` + `card.rs` + `reader.rs`, split 2026-08-11 from a 1749-line `nfc.rs`) is the source of truth for signing, validation, codec, and NFC framing. The canister, relay, sim, fixture, and FFI all import it; the app reaches it via UniFFI → `libdpay_ffi.so`. There is no parallel JS/Kotlin reimplementation of money logic.
- Money-critical JS (`app/payments.ts`) is intentionally pure + jest-tested and stays on outcome classification (settled/rejected/unknown), never on signature math. Correct separation.
- **The RN app is modular, not monolithic** (`app/App.tsx`, split 2026-07-31). The root (`App.tsx`, 110 lines) only loads identity + relay, runs the self-check, and routes `Onboarding | Wallet`; everything else lives behind a strictly-layered module tree — `config/` (palette, constants incl. `POLL`, currency catalog), `lib/` (types + pure format helpers + the clipboard/deep-link utilities moved from `hooks/` in the PR23-30 DRY pass), `hooks/` (TRUE React hooks — `useHotkeys`/`useEscapeToClose` plus the three Wallet data hooks extracted in the Phase-5 de-god-component pass: `useCatalog`/`useBalancePoll`/`useTransactionHistory`, and the shared NFC tap state machine `useNfcTapState` extracted 2026-08-08 from the IC+SOL tap components; ## The canister is a FACADE over external ICRC ledgers (not the ledger)

`dpay-canister` (`ssqti`) holds **no balances**. It is a pure facade with three jobs plus the offline-payer authorization gate:

> **Module layout (2026-08-06, commit `e8ee866`; extended 2026-08-10 commit `484d9e0`):** the canister source is split across FOUR files — `types.rs` (1237 lines: all data types, `Storable` impls, encoding helpers, API structs, ckBTC/ckETH/ckERC20 mirror types, constants) + `calls.rs` (313 lines: all cross-canister call helpers — `ledger_*`/`minter_call_*`/`icrc2_approve`/`ledger_get_transactions` + pure value helpers `account_of`/`to_pubkey`/`nat_to_u64`/`dedup_created_at_time`) + `proxy.rs` (655 lines: the deposit/withdraw proxy surface extracted in M7 — `require_btc_family_minter()` family-gate helper (M6) + the `deposit_address`/`refresh_deposit`/`deposit_info`/`withdraw` family-dispatch bodies) + `lib.rs` (1547 lines: `thread_local!` statics, nonce management, guards, `write_cache`/`ensure_receipt_key`/`record_txn`, all 26 `#[init]`/`#[update]`/`#[query]` entry points, `export_candid!()`). All split-out items are `pub(crate)`; candid-exported types stay `pub`. The split is purely structural — the candid interface, the 81+ PocketIC tests, and all entry points are byte-for-byte unchanged.

1. **index** — a registry `currency(u32) -> {ledger principal, mintable}` (`LEDGERS`, stable), populated at init and extendable via `register_ledger`.
2. **routing** — `pay()` resolves the wire's `currency` to its ledger and settles there via the uniform ICRC interface (`icrc1_transfer` / `icrc1_balance_of` / `icrc1_fee`).
3. **cache** — a display-only `BAL_CACHE` backs the fast `balance_of` *query*.

PLUS the **authorization gate** (Ed25519 sig verify + nonce replay protection + expiry/cap), which stays *in the facade* — that is the offline-payer value-add, not ledger logic. Every currency = one real ICRC ledger canister (the DFINITY `ic-icrc1-ledger`); the facade routes every payment through this one interface.

PLUS a **deposit-proxy surface** (ckBTC-style top-up) — four `#[update]` endpoints that proxy an external chain-key minter so the wallet can show a per-account native deposit address, poll for a confirmed mint, and read static deposit instructions: `deposit_address` / `refresh_deposit` / `deposit_info` (no auth — see risk 7) plus `register_minter` (admin-gated by the same `require_admin` controller as `register_ledger`). The minter principal per currency lives in a separate stable map `MINTERS` (`MemoryId 8`; value = `PrincipalStorable`, a principal newtype that serializes the raw ≤29 bytes with no present-flag — absence is expressed by map membership). **KEY INVARIANT:** the minter is always called with `owner = Some(canister_self())`, `subaccount = Some(pubkey)` (`minter_call_btc_address` / `minter_call_update_balance`, lib.rs), so the mint lands on the currency's ICRC ledger at exactly `Account{owner: facade, subaccount: pubkey}` — the *same* account `account_of` (lib.rs:578) hands to `icrc1_balance_of` / `pay` / `transactions_of`. **Subtle encoding requirement (load-bearing):** the REAL ckBTC minter (`mqygn-kiaaa-aaaar-qaadq-cai`, verified via `dfx canister metadata … candid:service --network ic`) takes exactly ONE record argument `(record { owner: opt principal; subaccount: opt blob })` for `get_btc_address` / `update_balance`. The facade encodes this as a candid **1-tuple** `(MinterAccount{ owner, subaccount },)` passed via `Call::with_args(&arg)` — `with_args` on a 1-tuple emits ONE argument (the record). A 2-tuple `(Option<Principal>, Option<Vec<u8>>)` would instead emit TWO positional args and the real minter TRAPS with `IC0503 ... Fail to decode argument 0 ... Subtyping error: Type mismatch` (this exact trap shipped to mainnet once; see below). The single/zero-arg minter proxies and all ledger calls are unaffected. This invariant is pinned by the PocketIC deposit test + a direct mock-contract honesty guard (see "Offline proof status" below). The deposit surface is therefore **purely informational + orchestration**: it changes nothing about settlement, balance, or history — once a mint confirms, the existing balance/history reads reflect it with no code change. dpay never holds the deposited BTC (the minter does the chain-key work and credits the ledger directly), so the non-custodial posture is intact.

**Money-safety rule (load-bearing):** `pay()` ALWAYS reads the AUTHORITATIVE ledger balance (`icrc1_balance_of`) before transferring. The cache is DISPLAY-ONLY — a stale cache (someone transferred directly on the ledger) can only make a shown number wrong, never cause a bad settlement. The cache is refreshed after successful `pay` / `mint` / `burn`. ✅ **RESOLVED (MC3 U1 + U2, 2026-08-02):** the facade exposes an authoritative on-demand `refresh_balances(pubkey, currencies)` update (single + batch via the SAME call — pass `[currency]` for one, every registered id for all; re-reads the ledger via `icrc1_balance_of` for each REQUESTED currency + writes `BAL_CACHE` + returns the entries; no auth gate — a read + cache write moves no value, consistent with the unauthenticated `balance_of`/`deposit_address` surface), and `refresh_deposit` inline-refreshes the cache after every successful minter call (both the `Ok(statuses)` mint branch AND the `NoNewUtxos` poll branch — so a freshly-minted ckBTC deposit is immediately visible via `balance_of` WITHOUT an extra refresh, and the 10s poll catches coincident direct transfers / async ckERC20 heartbeat mints for free). The cache refresh is deliberately NOT added to the AlreadyProcessing/TemporarilyUnavailable/GenericError branches (the minter call failed there — cache state unknown). **U2 (relay freshness contract — query-first + batch refresh since 2026-08-08):** the relay's `Ledger::balance` path is a PURE fast cached `balance_of` query (~200ms QUERY, no consensus) — it NO LONGER fires a per-currency refresh. The authoritative refresh moved to a SINGLE batch: the `/balances` handler calls `Ledger::refresh_all_if_stale(pubkey)` ONCE after the fan-out, which — when ANY currency for the pubkey is stale (or on cold start) — spawns ONE `refresh_balances` UPDATE on a detached tokio task (`AgentLedger::spawn_background_refresh_all`) that fetches the catalog, passes every registered currency id, does N inter-canister `icrc1_balance_of` calls inside a SINGLE consensus round, and writes each to `BAL_CACHE`. This collapses the old N per-currency background spawns (each its own 2-5s consensus round) into one. The TTL decision lives in the RELAY (`AgentLedger.last_refresh: Arc<Mutex<HashMap<(pubkey, currency), Instant>>>` — `Arc` so the background task can mark every currency fresh on success), not the canister; a cold start / relay restart just fires one batch refresh and returns the last cached value immediately, never wedging the response. (Before the batch change a cold start fired 6 parallel UPDATEs through consensus; now it fires ONE. The canister's `BAL_CACHE` persists across relay restarts, so returning the cached query immediately is safe — facade-bypassing credits surface within one batch-refresh cycle. Failures log the pubkey/error and leave the entries stale for the next poll; `refresh_balances` is idempotent so overlapping tasks on a slow replica are safe.) `FakeLedger` is untouched (already authoritative in-memory; its `refresh_all_if_stale` is the default no-op). Proven on PocketIC: the canister `refresh_deposit_makes_minted_balance_visible_via_balance_of` + `refresh_balances_reflects_a_cache_bypassing_credit` + `refresh_balances_refreshes_every_currency_when_passed_all`/`refresh_balances_is_idempotent` (facade path), and the relay `balance_and_batch_refresh_are_authoritative_after_cache_bypass_credit` (balance() is a pure stale query → `refresh_all_if_stale` fires the batch → cache refreshed → within-TTL second call is a no-op).

## Withdrawal proxy (ckBTC → BTC / ckETH → ETH out) — family-dispatched, the one-way valve's other direction

`withdraw(WithdrawRequest)` is the mirror of the deposit proxy: where `refresh_deposit` mints a chain-key asset IN, `withdraw` burns it OUT to a native address on a **verified user Ed25519 signature** (the non-custodial gate — the facade rebuilds the canonical `WithdrawAuth` from the candid fields, recomputes `signing_bytes()` in `dpay-core`, and verifies the sig under `from_pubkey` == the debit subaccount BEFORE moving funds). **Family dispatch (M0):** the currency's registered `minter_family` (+ `token_contract` for ckERC20) selects the minter method after the shared sig/expiry/nonce preamble: `CkBtcUtxo` → `icrc2_approve(amount)` + minter `retrieve_btc_with_approval` (single-use allowance, BTC floor `RETRIEVE_BTC_MIN_AMOUNT = 50_000` sats applied in THIS branch only); `CkEthErc20` + `token_contract None` → `eip_1559_transaction_price` → `icrc2_approve(amount + max_transaction_fee)` + minter `withdraw_eth` (a single running-balance allowance covers the `amount` burn NOW + the gas-fee burn LATER — DIFFERENT approve semantics from ckBTC; no local Wei floor, the minter enforces `minimum_withdrawal_amount` and returns `AmountTooLow`); `CkEthErc20` + `token_contract Some` → the DUAL-ledger `withdraw_erc20` path (RESOLVED — was fail-closed): resolve the registered `gas_ledger` (the ckETH ledger, `currency_gas_ledger(currency)`; **None → fail-closed** — cannot fall through to native-eth `withdraw_eth`, which would mis-burn the amount as ckETH), query `eip_1559_transaction_price(Some(ckerc20_ledger_id))`, then `icrc2_approve(gas_fee)` on the **ckETH gas ledger** + `icrc2_approve(amount)` on the **ckERC20 amount ledger** (two separate approves), then minter `withdraw_erc20`. A currency with no family meta but a registered minter defaults to `CkBtcUtxo` (legacy default — preserves ckBTC deployments that registered a minter but no family meta); a currency with NO family meta AND NO registered minter now **fails-closed** with `Err("no minter family and no minter")` (2026-08-07, `39c83a7` — closes the DEMO play-money default path; proven by `withdraw_failclosed_no_minter_no_family`). `icrc2_approve` takes a candid `Nat` (not u64) so the ETH `amount + fee` sum cannot overflow. Idempotency mirrors `pay`: the withdraw nonce is reserved synchronously (no await) in a SEPARATE `WITHDRAW_NONCES` map (MemoryId 12) before any cross-canister call; released on a transient/pre-burn failure (same-auth retryable); settled once the burn commits or on a permanent minter error (AmountTooLow / RecipientAddressBlocked / TokenNotSupported / MalformedAddress — dead auth; the user must sign fresh). The amount-ledger approve failure (after the gas-ledger approve succeeded) → RELEASE (an approve is an allowance grant, not a burn — nothing moved; retryable). The ckERC20 PARTIAL failure (`CkErc20LedgerError` — gas burn SUCCEEDED, amount burn FAILED → minter schedules a gas reimbursement) → SETTLE (terminal; funds DID move — the ckETH gas debit — so the dead auth can never replay, preventing a second gas burn). `CkEthLedgerError` (gas burn itself failed → nothing moved) → RELEASE/SETTLE by inner `LedgerError` (transient → release; AmountTooLow → settle). Proven offline on PocketIC through the real facade + `dpay-mock-minter` (BTC: `tests/withdraw.rs`; ETH: `tests/withdraw_eth.rs` — dispatch-proof via amount-below-BTC-floor succeeding, debit+burn, double-withdraw/wrong-sig/expired/below-min rejected, mock-minter honesty guards for BOTH minter surfaces). The relay surfaces it at `POST /api/v1/withdraw` (`Ledger::withdraw` trait + `FakeLedger`/`AgentLedger` impls) and the app's `WithdrawSheet` signs on-device via the FFI's `sign_withdrawal`.

**Residual front-running risk (documented, inherent to `retrieve_btc_with_approval` / `withdraw_eth` / `withdraw_erc20`):** the approve + retrieve/withdraw are two cross-canister calls with an `await` between them; in principle a separate caller could invoke the minter with the same subaccount + an attacker address in the gap, consuming the allowance. The blast radius is bounded to the EXACT authorized `amount` (+ the gas fee for ckERC20, a separate small approval) — never the user's whole balance. This is inherent to the ckBTC/ckETH withdrawal design (the minters have no signature-binding-the-destination path); the reference NNS minter clients accept the same residual. The ckERC20 `withdraw_erc20` path extends this to TWO ledgers (gas + amount), each approved separately. See risk 8.

## Where the design earns its keep

- **Consent model is sound.** `PaymentRequest` carries no `from`/sig; `to_authorization(from)` copies everything verbatim, so the payer's signature binds exact amount+payee+nonce+currency. The `request_id` doubling as the nonce is elegant — single-scan single-use kills double-charge by construction.
- **Per-currency segregation is across *canisters*, the strongest no-swap guarantee.** A user pubkey maps to ICRC-1 `Account{owner: <facade>, subaccount: <pubkey>}` on each ledger independently. Funds in currency X physically cannot be drawn by a payment naming currency Y — they live on a different ledger canister. This is stronger than a per-currency map key inside one canister. Proven by `currencies_cannot_cross`.
- **Cross-canister atomicity + replay safety is handled honestly.** `pay()` spans `await`s (balance/fee/transfer), and the IC interleaves messages at await points. The nonce is **reserved synchronously before any transfer** (no await in the reserve), so a concurrent `pay` with the same nonce observes it as used and is rejected. Proven by `concurrent_pay_same_nonce_settles_once` (the double-spend regression). On a transient ledger failure the reservation is released (same nonce retriable); on `Ok`/`Duplicate`/permanent-error it stays spent. Defense-in-depth: `created_at_time` is quantized so a sequential retry of the same authorization lands in the ledger's `Duplicate` bucket → no second debit. (The airtight close is an `icrc3_get_blocks` reconcile on restart — a production item, not yet implemented.)
- **NFC transport reuses the exact QR bytes.** Same 292-byte wire (now 2 ISO-DEP frames — 292 > `DEFAULT_MAX_CHUNK`(240); was 1 frame pre-v2), same `verify()`. The HCE/reader state machines are panic-free (`card_never_panics_on_arbitrary_input` proptest) and carry a `SessionPhase` the UI renders directly. ## Stable-memory layout (upgrade compatibility)

State lives in stable structures so it survives upgrades automatically (no `pre_upgrade`/`post_upgrade`). The facade preserves the pre-facade shipping canister's `SPENT` (MemoryId 1, value `()` — a set), `CAP` (2), `TXN_SEQ` (3), and `ACCOUNT_TXNS` (4) at the **same** MemoryIds/types, so an in-place upgrade of `ssqti` keeps nonces + history. The legacy internal `BALANCES` (MemoryId 0) is abandoned-and-inert (orphaned play money; unread by the facade). New facade state uses fresh MemoryIds: `LEDGERS` (5), `CONTROLLER` (6), `BAL_CACHE` (7), `MINTERS` (8), `FAUCET_COOLDOWN` (9 — `(currency,pubkey)`→last-faucet secs, backs the self-service faucet rate-limit; value type `u64`, key reuses `CacheKey`), `RECEIPT_SECRET` (10 — the canister's receipt Ed25519 secret, `Option<[u8;32]>` in a `StableCell`; generated once via `raw_rand`, never rotated), `RECEIPTS` (11 — `nonce`→`StoredReceipt`{canonical claim bytes[108]+sig[64]}, backs `receipt(nonce)`), `WITHDRAW_NONCES` (12 — `nonce`→`()`, the withdrawal idempotency set; a SEPARATE map from `SPENT` so a withdraw nonce can't collide with/block a pay nonce, mirroring `SPENT`'s reserve/release/settle semantics for the `withdraw` path), `CURRENCY_META` (13 — `currency`→`CurrencyMetaStorable`{opt symbol + opt decimals + opt minter_family byte}; backs the `currencies()` catalog + `MinterFamily` ramp-dispatch key, M0). `MINTERS`'s value is the `PrincipalStorable` newtype (raw ≤29 principal bytes; `BOUND = Bounded{29, is_fixed_size:false}`) — a separate map so the existing `LedgerEntry{principal, mintable}` encoding on MemoryId 5 is untouched. NB: `SPENT` keeps value type `()` rather than a 1-byte Pending/Settled enum — reusing a MemoryId with a different value size would corrupt the B-tree on upgrade, and `contains_key` (the sole read) makes the set semantically equivalent. The MemoryId/type compatibility (1–4 reused with identical key/value layout; 5/6/7/8/9/13 on fresh MemoryIds; 0 abandoned-and-inert) is **verified by inspection** of the `thread_local!` block — it is not proven by a cross-version test. The regression test `upgrade_preserves_nonces_and_history` covers **stable-structure survival across an upgrade round-trip**, but note it upgrades facade → *same*-facade wasm, so it proves the stable-structure round-trip, NOT the real old-internal-canister → facade layout. **Recent-blockhash v2 model (the active offline-pay rail — 2026-08-13 rewrite retired durable-nonce):** the merchant mints a `solreq:v2` URI carrying a fresh recent blockhash (`bh`) + a short validity window (`iat`<`exp`≤`iat`+90s). The payer signs fully offline: builds the canonical message `{Memo(ix0), System.transfer(ix1)}` (SOL) or `{Memo(ix0), Token.transferChecked(ix1)}` (USDC) with `recentBlockhash = bh`, signs with the device key, and emits a `solpay:v2` URI. The merchant strict-verifies the canonical message bytes + the single payer signature via `verifySolPayment` BEFORE broadcast (BLOCKING — a mismatch is refused, not warned). **No nonce account, no setup step, no rent reserve, no advance ix** — strictly simpler than the durable-nonce design it replaced. **v2 invariants (load-bearing):** (1) **short validity** — the blockhash expires (~60-90s of slots), so `exp` is tight and expiry enforcement is REAL (an expired `solreq:v2` is refused at scan, not decorative); (2) **unknown-outcome** — a payment signed offline may be broadcast after the blockhash expires (the payer went offline, the merchant was slow) → Solana rejects the stale blockhash and the tx never lands; the UI surfaces this as honest pending/unknown, NOT a guaranteed settle (unlike IC's atomic canister settle). Replay protection = the request `rid` (single-use at the merchant/relay layer) + the blockhash's own expiry. **Construction proven byte-exact vs `@solana/web3.js`** (jest goldens in `app/__tests__/solana-tx.test.ts` + `solana-spl.test.ts`); the v2 self-check (`runSolSelfCheck`) exercises the full build/sign/verify path on-device.

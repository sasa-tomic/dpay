# dpay codebase analysis

> **Living document.** This is a structural analysis of the dpay codebase — architecture health, where the design earns its keep, and risks to flag before a coding session. It is maintained alongside the code: when a change materially affects anything stated here (a risk resolved, a new surface added, an invariant changed), update this file in the same change.
>
> Last reviewed: see `git log` for this file. Scope: everything under the workspace (`dpay-core`, `dpay-canister`, `dpay-canister-tests`, `dpay-mock-minter` [test-only], `dpay-relay`, `dpay-ffi`, `dpay-sim`, `dpay-fixture`, `ui/`, `app/`).

## Architecture health: strong

The single most load-bearing decision — **one Rust core shared by every consumer** — is actually enforced everywhere:

- `dpay-core` (`lib.rs` 454 lines + `nfc.rs` 1663 lines) is the source of truth for signing, validation, codec, and NFC framing. The canister, relay, sim, fixture, and FFI all import it; the app reaches it via UniFFI → `libdpay_ffi.so`. There is no parallel JS/Kotlin reimplementation of money logic.
- Money-critical JS (`app/src/payments.ts`) is intentionally pure + jest-tested and stays on outcome classification (settled/rejected/unknown), never on signature math. Correct separation.

The wire format is frozen and byte-precise (`SIGNING_LEN=100`, `WIRE_LEN=196`, `REQUEST_LEN=68`), and `validate()` is pure/allocation-free — exactly what a canister hot path wants. Field order is documented as FROZEN, which is the right discipline for a protocol surface.

## The canister is a FACADE over external ICRC ledgers (not the ledger)

`dpay-canister` (`ssqti`) holds **no balances**. It is a pure facade with three jobs plus the offline-payer authorization gate:

1. **index** — a registry `currency(u32) -> {ledger principal, mintable}` (`LEDGERS`, stable), populated at init and extendable via `register_ledger`.
2. **routing** — `pay()` resolves the wire's `currency` to its ledger and settles there via the uniform ICRC interface (`icrc1_transfer` / `icrc1_balance_of` / `icrc1_fee`).
3. **cache** — a display-only `BAL_CACHE` backs the fast `balance_of` *query*.

PLUS the **authorization gate** (Ed25519 sig verify + nonce replay protection + expiry/cap), which stays *in the facade* — that is the offline-payer value-add, not ledger logic. Every currency = one real ICRC ledger canister (the DFINITY `ic-icrc1-ledger`); the facade routes every payment through this one interface.

PLUS a **deposit-proxy surface** (ckBTC-style top-up) — four `#[update]` endpoints that proxy an external chain-key minter so the wallet can show a per-account native deposit address, poll for a confirmed mint, and read static deposit instructions: `deposit_address` / `refresh_deposit` / `deposit_info` (no auth — see risk 7) plus `register_minter` (admin-gated by the same `require_admin` controller as `register_ledger`). The minter principal per currency lives in a separate stable map `MINTERS` (`MemoryId 8`; value = `PrincipalStorable`, a principal newtype that serializes the raw ≤29 bytes with no present-flag — absence is expressed by map membership). **KEY INVARIANT:** the minter is always called with `owner = Some(canister_self())`, `subaccount = Some(pubkey)` (`minter_call_btc_address` / `minter_call_update_balance`, lib.rs:644–662), so the mint lands on the currency's ICRC ledger at exactly `Account{owner: facade, subaccount: pubkey}` — the *same* account `account_of` (lib.rs:578) hands to `icrc1_balance_of` / `pay` / `transactions_of`. **Subtle encoding requirement (load-bearing):** under ic-cdk 0.19 the minter's `(Option<Principal>, Option<Vec<u8>>)` argument tuple MUST be passed via `Call::with_args(&tuple)` (calls `encode_args` = a multi-arg candid tuple), NOT `with_arg(tuple)` (calls `encode_one` = a single argument, which silently drops the subaccount to `None` and routes every deposit to the canister's default subaccount). The single/zero-arg minter proxies and all ledger calls are unaffected. This invariant is verified by the PocketIC deposit test (see "Offline proof status" below). The deposit surface is therefore **purely informational + orchestration**: it changes nothing about settlement, balance, or history — once a mint confirms, the existing balance/history reads reflect it with no code change. dpay never holds the deposited BTC (the minter does the chain-key work and credits the ledger directly), so the non-custodial posture is intact.

**Money-safety rule (load-bearing):** `pay()` ALWAYS reads the AUTHORITATIVE ledger balance (`icrc1_balance_of`) before transferring. The cache is DISPLAY-ONLY — a stale cache (someone transferred directly on the ledger) can only make a shown number wrong, never cause a bad settlement. The cache is refreshed (re-read from the ledger) after every successful `pay` / `mint` / `burn`.

## Where the design earns its keep

- **Consent model is sound.** `PaymentRequest` carries no `from`/sig; `to_authorization(from)` copies everything verbatim, so the payer's signature binds exact amount+payee+nonce+currency. The `request_id` doubling as the nonce is elegant — single-scan single-use kills double-charge by construction.
- **Per-currency segregation is across *canisters*, the strongest no-swap guarantee.** A user pubkey maps to ICRC-1 `Account{owner: <facade>, subaccount: <pubkey>}` on each ledger independently. Funds in currency X physically cannot be drawn by a payment naming currency Y — they live on a different ledger canister. This is stronger than a per-currency map key inside one canister. Proven by `currencies_cannot_cross`.
- **Cross-canister atomicity + replay safety is handled honestly.** `pay()` spans `await`s (balance/fee/transfer), and the IC interleaves messages at await points. The nonce is **reserved synchronously before any transfer** (no await in the reserve), so a concurrent `pay` with the same nonce observes it as used and is rejected. Proven by `concurrent_pay_same_nonce_settles_once` (the double-spend regression). On a transient ledger failure the reservation is released (same nonce retriable); on `Ok`/`Duplicate`/permanent-error it stays spent. Defense-in-depth: `created_at_time` is quantized so a sequential retry of the same authorization lands in the ledger's `Duplicate` bucket → no second debit. (The airtight close is an `icrc3_get_blocks` reconcile on restart — a production item, not yet implemented.)
- **NFC transport reuses the exact QR bytes.** Same 196-byte wire, same `verify()`. The HCE/reader state machines are panic-free (`card_never_panics_on_arbitrary_input` proptest) and carry a `SessionPhase` the UI renders directly. AID registered under `category="other"` deliberately to avoid the Google Wallet clash — a subtle real-world trap handled correctly.
- **Relay is honest about failure modes.** `LedgerError::{Rejected(422), Transient(503)}`, retry only on Transient, idempotency keyed by nonce, `committed` guard stops transport errors overwriting a decided ledger outcome, reconcile via `/receipt/:nonce` before reporting failure. This is the "relay must be rock solid" requirement, met. The `Ledger` trait + `AgentLedger` are canister-agnostic (the relay targets the facade `ssqti` by configured id); the only facade-specific detail is that `mint`/`burn` are controller-gated `Result<nat64,text>` updates — `mint` returns the **new balance** (matching the `Ledger::mint` contract that the faucet surfaces directly as `{balance}`), `burn` returns the ledger block index (facade-internal, no relay consumer). Both are decoded in `AgentLedger`.
- **Durable transaction history is ledger-sourced-of-effect, locally indexed.** The facade appends every settled payment to a per-(account, currency) stable-memory index (`ACCOUNT_TXNS`, key = `pubkey|currency|seq_be`, stored under both `from` and `to`) and exposes `transactions_of(blob, nat32, nat32) -> vec` (newest-first, survives upgrades). `mint`/`burn` are recorded too (counterparty = the `MINT_ACCOUNT` sentinel). The query path uses `StableBTreeMap::range(..).rev().take(limit)` — O(limit), not O(total) — which matters because the wallet polls it every 5s.
- **The deposit/top-up surface reuses the exact account model — by construction, not coincidence.** The ckBTC-style deposit proxy (`deposit_address` / `refresh_deposit` / `deposit_info` + admin `register_minter`) calls the ck minter with `owner = canister_self()`, `subaccount = pubkey`, so a confirmed mint lands at the very `Account` `pay`/`balance_of`/`transactions_of` already read. Zero settlement/balance/history code changed — the deposit feature is a pure informational+orchestration layer on the facade, and a deposit that confirms is *automatically* the next balance poll's number. The relay surfaces it symmetrically: three new `Ledger` trait methods (`deposit_address` / `deposit_status` / `deposit_info`, `ledger.rs:167`) and three REST routes (`GET /api/v1/deposit/address/{hex}`, `POST /api/v1/deposit/refresh/{hex}`, `GET /api/v1/deposit/info`, `app.rs:122`). Per the plan's §0 error rule the proxy has **no permanent-policy failure** (no sig/cap/replay), so all three map any `LedgerError` → HTTP **503** — there is deliberately no `422` path (contrast `pay`/`faucet`, which keep `Rejected`→422). `FakeLedger` simulates the mint with a `pending_deposits` map + a `register_deposit` test hook (drain-and-credit on `deposit_status`); `AgentLedger` proxies the facade and normalizes the minter's candid `Nat` block index to a JSON-safe `String`. The relay layer is covered by unit tests (`tests/relay.rs`: address determinism, `deposit_status` drains+credits, and the HTTP route).

## A radical e2e harness drives the REAL app (15 flows; supersedes the old ui/ harness)

`e2e/` (its own npm package) is the flow-verifier the project was missing — it renders the **real** `app/App.tsx` (unmodified) in `react-native-web` + headless chrome, against the **real** test relay (FakeLedger, offline), and drives the wallet through real UI flows. It is NOT a parallel-component harness (the old `ui/` rendered `ui/src/App.jsx`; **`ui/` is now deleted** — `e2e/` drives the real app AND screenshots every flow state into `e2e/shots/`, so the golden-shot function is fully migrated). Every line of the app's TS — `payments.ts`, the wallet state machine, the fetch calls — runs verbatim. Only the I/O boundary is shimmed:

- **`DpayCore` signing shim (CRITICAL — byte-exact):** `e2e/web/dpay-core.ts` implements Ed25519 sign/verify/encode/decode over `@noble/ed25519`, reading field offsets/lengths/endian from `dfx/wire_layout.json` (the single source of truth, generated by `cargo run -p dpay-fixture --release -- wire-layout`). `e2e/tests/00-cross-val.mjs` re-signs the golden Authorization with the shim and asserts byte-identical sig + wire to the Rust core, proving local pay flows will settle on the real FakeLedger (which calls `sa.verify()`). The shim is installed into `react-native-web`'s `NativeModules.DpayCore`, so the app reads it via the **same** `const {DpayCore} = NativeModules` seam as on-device. (`e2e/harness/wire.mjs` exposes the same pure byte builders + signing Node-side, so flows 06/07/09/10 build/decode requests + sign authorizations with the real key without re-deriving the math.)
- **Camera scan** — `react-native-vision-camera` stub; `useCodeScanner` fans `window.__DPAY_TEST_SCAN(<string>)` to the app's `onCodeScanned` (smallest boundary — the app's downstream decode/submit logic runs unchanged). Flows 07/10 inject a second wallet's request QR this way.
- **DpayNfc + NFC session seam (WIRED to the real bus, audited):** the native-module surface is a no-op stub, and `window.__DPAY_TEST_NFC_SESSION(event)` emits `DpayNfcEvent`s through a `react-native-web` `NativeEventEmitter` instance — i.e. the SAME global `RCTDeviceEventEmitter` bus the app's `new NativeEventEmitter(DpayNfc).addListener('DpayNfcEvent', …)` listens on (an earlier scaffold used a private registry that never reached the app). **Audit (verified, not a shortcut):** RNW's `RCTDeviceEventEmitter` is a single module-level singleton (`export default new EventEmitter()` — one instance in the built bundle), and `NativeEventEmitter.addListener`/`emit` BOTH delegate to that exact singleton (`addListener`→`RCTDeviceEventEmitter.addListener`, `emit`→`RCTDeviceEventEmitter.emit`), keyed by event name; the `_nativeModule` arg only drives the `addListener`/`removeListeners` lifecycle callbacks (no-ops in the shim), NOT event routing. So the seam's `nfcBus.emit('DpayNfcEvent', e)` reaches the app's listener through the IDENTICAL singleton — the app reads no global the shim writes (no private registry, no global shortcut). The behavioral proof is flow 11: a seam-dispatched `phase` event advances the app's REAL NfcTap state machine (linking→exchanging→success), which is only possible if the app's listener fired on the real bus. `DpayCore.nfcStatus` reads `window.__DPAY_TEST_NFC_STATUS` (default `'unknown'` → the NfcPill stays hidden); flow 11 flips it to `'ready'` and drives the NfcTap state machine through every phase. The radio hop stays a physical-device gate; only the JS event plumbing is faked.
- **QR value seam** — the `react-native-qrcode-svg` shim stashes the exact value it encodes on `window.__DPAY_QR_LAST`, so flow 06 decodes the request QR's bytes field-for-field (to/amount/expiry/currency) rather than OCR'ing the SVG matrix.
- **Share** → noop resolving `{action:'dismissedAction'}` (the browser's `navigator.share` rejects in headless chrome). The deposit "Copy address" path no longer relies on Share: on web the real app calls `navigator.clipboard.writeText`, which the shim wraps to ALSO capture into `window.__DPAY_TEST_CLIPBOARD` (the e2e assertion target — proves the copy button hit the real clipboard, not the noop). On native the app falls back to the real `Share` sheet (Android exposes "Copy").
- **`?screen=` deep link** — the real app reads `?screen=deposit` on web (via `globalThis.location`, guarded by `Platform.OS === 'web'`) to auto-open the `DepositSheet`, so a returning user (identity in localStorage) lands directly on top-up; bookmarkable/shareable, and the harness deep-links tests straight in. Harmless on native (no URL bar).
- **react-native-qrcode-svg** — replaced with a `.tsx` shim (upstream ships only `.js` with JSX, which rolldown's parser rejects); same matrix→SVG path via the `qrcode` lib + `react-native-svg`.
- **`?relay=` query override** — `e2e/vite.config.js` aliases App.tsx's `./relayConfig` import to a runtime override that reads `?relay=` / `window.__DPAY_RELAY`, so the harness can point the app at the local test relay (or live) without touching App.tsx.
- **Keyboard surface (flow 14)** — the app's `useEscapeToClose` (web-only DOM `keydown`) closes an open sheet on Escape; the deposit sheet documents the shortcut in-UI ("Press Esc to close"). This is the seed of the keyboard-shortcuts surface; broader single-key primary actions are a documented follow-up.

CORS: the web app is served on a different port than the relay (sirv + axum); rather than add CORS headers to the prod relay JUST for the browser harness, the headless chrome is launched with `--disable-web-security` (test-only; matches what the real Android app sees — Android fetch doesn't enforce CORS).

Two modes via env: `DPAY_E2E_MODE=local` (default: spawns the test relay, offline) and `DPAY_E2E_MODE=live` (uses `DPAY_E2E_BASE`, no local relay; throwaway identities, throttled). Add a flow = add `e2e/tests/NN-name.mjs` exporting `async function run()`; `e2e/run.mjs` runs them sequentially with fail-fast. **Verify gate (green, 15/15):** `00-cross-val` (ed25519 byte-exact) → `01-onboard` → `02-faucet` (repeatable demo-$ top-up) → `03/04/05-deposit` (address+instructions / clipboard+Esc / **credited ckBTC top-up via the test-helpers seed route, proven on the currency-1 balance**) → `06-request-qr` (decodes the 68-byte request, fields verified) → `07-scan-pay` (two wallets, real sig + settle, A↓/B↑/history) → `08-merchant-settle` (recipient side) → `09-double-spend` (replay → `replayed:true`, no double-debit) → `10-expired` (422, no debit) → `11-nfc` (phases via the seam) → `12-settings` / `13-offline` (graceful) / `14-keyboard` (Esc). Stable testIDs ARE the contract (`btn-create`, `balance`, `btn-topup`, `btn-deposit`, `deposit-{address,instructions,status}`, `btn-deposit-{check,copy,close}`, `tab-{pay,receive}`, `amount-input`, `btn-request`, `request-qr`, `pay-amount`, `btn-approve`, `btn-new`, `nfc-{ready,status}`, `settings-relay`, `btn-reset`, `asset-ckbtc`). **Asset-segregation note (flow 05):** the `$` wallet header is DEMO_USD (currency 0); ckBTC deposits credit currency 1 — a separate asset (per-currency canister segregation). The wallet now SURFACES that ckBTC balance as a clearly-labeled `asset-ckbtc` "Bitcoin" card (currency 1, shown only when non-zero, on the same 2.5s poll) — the seamless top-up contract: after the deposit sheet closes the credited asset stays VISIBLE. The card is deliberately OUTSIDE the `$` header (CLAUDE.md hard rule: "Money shown as `$`, never token name"); the "Bitcoin" label + BTC units match the deposit instructions' network/asset name, never the primary balance. **Spendability:** the Pay flow is currency-aware — `signAuthorization(..., req.currency)` honors the currency the merchant's request QR carries (App.tsx:737/877), so ckBTC IS spendable when a merchant issues a currency-1 request; the demo's request QR defaults to currency 0 by PoC scope, not by a protocol limitation (a multi-currency merchant request UI is an honest follow-up, not faked). Flow 05 therefore proves the credited path on the deposit asset three ways: the sheet shows "Deposited ✓" + minted BTC, the relay's `?currency=1` balance grew, AND the wallet's `asset-ckbtc` card shows the minted BTC after the sheet closes. The `$` header is a different asset (DEMO_USD) and deliberately does not move.

**Speed / isolation:** the relay + web server + browser PROCESS are spawned ONCE per run and reused across tests; each test gets a FRESH incognito browser context (fresh localStorage → fresh identity) against the shared relay, whose only cross-test state is the collision-free spent-nonce set + the faucet (funds each test's own distinct account) — no account-state leakage. The suite runs tests in a BOUNDED PARALLEL pool (`run.mjs`; `DPAY_E2E_CONCURRENCY=N`, default 6, `1` = sequential for debugging): full suite ~12s for 15 real-browser flows (vs ~60s sequential). **Concurrency-safety proof:** FakeLedger holds ALL state (balances, spent nonces, txns, pending deposits) behind ONE `Mutex<FakeState>` (`ledger.rs`) and the relay's idempotency cache is `Arc<Mutex<HashMap>>`, so concurrent requests serialize on the lock; each test onboards a DISTINCT random 32-byte pubkey → distinct `(pubkey, currency)` balance keys → no collision, and each payment nonce is a random 16-byte value → collision-free; reads are account-scoped; screenshots use distinct filenames. So N parallel contexts against the one relay touch DISJOINT account/nonce keys — parallelism changes no assertion and adds no coupling. Fail-fast: the first RED test stops new tests from STARTING (in-flight drain + "(not run — fail-fast)" markers, then non-zero exit). **E2e relay binary isolation (root fix for the always-rebuild workaround):** the e2e relay MUST carry `--features test-helpers` (the `/api/v1/test/deposit/seed` route), but `just check`/`just test-relay` build the SAME crate WITHOUT the feature into the SHARED `target/debug/dpay-relay` → clobber. The harness builds its relay into a DEDICATED `.dev/target-e2e` (gitignored; deps cache shared via `.dev/cargo`) so nothing else writes the e2e binary — cargo's fingerprinting there is authoritative, build-if-missing replaces the old always-rebuild, and `just e2e` is clobber-immune after `just check`. A post-spawn stateless probe (POST `/test/deposit/seed` with a 4-byte account → `400`, never touching the ledger) is a SAFETY NET that force-rebuilds once if the route ever 404s. `just verify = check e2e` (the old `ui` recipe is gone).


## Stable-memory layout (upgrade compatibility)

State lives in stable structures so it survives upgrades automatically (no `pre_upgrade`/`post_upgrade`). The facade preserves the pre-facade shipping canister's `SPENT` (MemoryId 1, value `()` — a set), `CAP` (2), `TXN_SEQ` (3), and `ACCOUNT_TXNS` (4) at the **same** MemoryIds/types, so an in-place upgrade of `ssqti` keeps nonces + history. The legacy internal `BALANCES` (MemoryId 0) is abandoned-and-inert (orphaned play money; unread by the facade). New facade state uses fresh MemoryIds: `LEDGERS` (5), `CONTROLLER` (6), `BAL_CACHE` (7), `MINTERS` (8), `FAUCET_COOLDOWN` (9 — `(currency,pubkey)`→last-faucet secs, backs the self-service faucet rate-limit; value type `u64`, key reuses `CacheKey`). `MINTERS`'s value is the `PrincipalStorable` newtype (raw ≤29 principal bytes; `BOUND = Bounded{29, is_fixed_size:false}`) — a separate map so the existing `LedgerEntry{principal, mintable}` encoding on MemoryId 5 is untouched. NB: `SPENT` keeps value type `()` rather than a 1-byte Pending/Settled enum — reusing a MemoryId with a different value size would corrupt the B-tree on upgrade, and `contains_key` (the sole read) makes the set semantically equivalent. The MemoryId/type compatibility (1–4 reused with identical key/value layout; 5/6/7/8/9 on fresh MemoryIds; 0 abandoned-and-inert) is **verified by inspection** of the `thread_local!` block — it is not proven by a cross-version test. The regression test `upgrade_preserves_nonces_and_history` covers **stable-structure survival across an upgrade round-trip**, but note it upgrades facade → *same*-facade wasm, so it proves the stable-structure round-trip, NOT the real old-internal-canister → facade layout. ## Risks worth flagging before a coding session

**1. Canister controller is unaddressed in code.** `CLAUDE.md` calls this out as load-bearing ("whoever can upgrade can set fee=100%"), but there is no blackhole/SNS wiring visible — the canister ships with whatever controller `dfx`/PocketIC assigns. Fine for PoC; must be settled before any pilot. This is the single biggest "property vs promise" gap. (Distinct from the in-canister *governance* controller below — that gates admin *methods*, not code upgrades.)

**2. `mint`/`burn`/`register_ledger`/`register_minter` are open when no governance controller is set.** ✅ **RESOLVED (R1).** The privileged admin ops are now **denied when `controller == null`** (`require_admin` flips from open-when-null to denied-when-null): a deployment that forgets to seed a governed controller cannot have its currency repointed or its demo currency printed by any caller. The demo's self-service on-ramp is now a **separate `faucet(account, currency)` method** that mints a FIXED constants-sourced amount (`FAUCET_AMOUNT = 10_000` = $100.00) and is **rate-limited per (account, currency)** via the stable `FAUCET_COOLDOWN` map (MemoryId 9, one mint per `FAUCET_COOLDOWN_SECS` = 1h window) — no admin gate. The relay's `/faucet` route calls `Ledger::faucet` (the `Ledger::mint` trait method is gone: the relay has no admin-mint path, it is not the controller). The faucet mints the fixed amount regardless of what a client asks (the canister ignores the requested `amount`; the permissive `FakeLedger` honors it as play money for the offline demo — a documented divergence). Proven on PocketIC: `open_mode_denies_admin_but_faucet_and_lockdown_work`, `controller_rotation_is_two_step`, `faucet_mints_fixed_amount_and_rate_limits`. `set_controller` keeps a one-time open-mode lockdown (callable when null) + two-step rotation once locked; the production path is to seed a governed principal at `init` (see risk 1 / docs/GOVERNANCE.md). (`provision_ledger_canister` and `transfer_cycles` remain separately gated by the fixed `ADMIN_CALLERS` operator allowlist — rotate to an SNS/governance principal before production.)

**3. Receipt is unsigned.** Documented and defensible for PoC (the payer's sig already binds amount/payee/nonce, so a lying merchant only hurts themselves), but it means the payer's "Paid ✓" rests on merchant honesty for the *outcome*, not just the *terms*. `CLAUDE.md` notes a canister-signed receipt as production hardening — that's the right upgrade path.

**4. Cross-canister trap window (residual, mitigated).** If the canister *traps* between the ledger committing `Ok` and `settle_nonce` completing, the IC rolls back this canister's message — including the nonce reservation — while the ledger's debit does NOT roll back (separate canister). A blind retry could then transfer again. Mitigated (not eliminated) by the quantized `created_at_time` dedup bucket (retries within a bucket → ledger `Duplicate` → success branch). The airtight close is an `icrc3_get_blocks` reconcile on restart — a production item. The dominant realistic trap source is stable-memory exhaustion in `record_txn`.

**5. `opt-level=1` in dev profile.** Speeds the inner loop but means proptest counterexamples run under light optimization — fine, just don't debug release-only miscompiles here.

**6. Transaction history is unbounded + single-page only (production roadmap).** Every settled payment writes two `TxnRecord`s, ~144B each, with no pruning and no cursor — a long-lived wallet grows without bound and can only fetch the newest ≤100 rows. Acceptable for the PoC/demo; before a pilot the history needs a paginated cursor, a retention window, or off-canister indexing. Not a correctness or money-safety issue (records are write-only-after-settle and never gate settlement).

**7. Deposit-proxy endpoints are unauthenticated (acceptable; documented).** `deposit_address` / `refresh_deposit` / `deposit_info` carry no caller gate — by design (plan §0): a deposit address is not secret (revealing it only lets someone send *to* the user), the minter methods are themselves permissionless (GeneralAvailability on mainnet), and `refresh_deposit` — the only value-creating one — is idempotent and a no-op when no UTXOs have confirmed (anyone triggering a real mint only credits the named pubkey). This is the right posture, with two operational invariants to keep: (a) a ck currency MUST have its minter `register_minter`'d at deploy — an unregistered minter surfaces as `Err("currency N has no ck minter")` → relay `Transient` → **503** (a deploy-time config invariant, not a runtime money risk); (b) on mainnet the facade principal must be **KYC-allowlisted** for ckBTC minting — a governance step, not code (the ckBTC minter mints only for KYC'd principals). ckETH/ckERC20 deposits reuse the same proxy seam but call different minter methods — a documented follow-up, **not built**.

> **Offline proof status — RESOLVED.** The deposit surface is proven end-to-end offline on PocketIC through the real facade. A test-only **mock-minter** canister exists at `crates/dpay-mock-minter/` (a workspace member; builds clean with `-D warnings`, zero warnings; never shipped to mainnet) — it reimplements the ckBTC minter's five methods (`get_btc_address` / `update_balance` / `register_deposit` / `get_minter_info` / `get_deposit_fee` / `get_known_utxos`) and mints onto a real `ic-icrc1-ledger` from the ledger's minting account.

# 2026-08-05 — Fresh-eyes UX audit

> Phase 6 deliverable of `2026-08-05-radical-e2e-and-polish.md`. READ-ONLY audit: no production code
> changed. The capture script is throwaway at `/tmp/opencode/ux-capture.mjs`. The ONLY repo file
> written by this audit is the one you are reading.

## Methodology

**Surface:** the real `app/App.tsx` rendered by react-native-web (Vite) and served by the existing
e2e harness, driven against the real test relay (FakeLedger, offline). No mocks in app code.

**Capture:** the throwaway `/tmp/opencode/ux-capture.mjs` script reuses `e2e/harness/lib.mjs`'s
`setup()` + `onboardWallet()` + relay helpers (`seedDeposit`, `refreshDeposit`, `pickFreePort`) +
`e2e/harness/wire.mjs`'s `generateKeypair` / `buildRequestQR` to drive the real UI through the full
user journey. Screenshots come from `driver.screenshot(name)` (headless chrome-headless-shell at
390×844, iPhone-12 viewport, with the harness's `FREEZE_CSS` for stable rendering).

**Analysis:** each PNG was passed to the `zai-vision` MCP (`analyze_image`) — the opencode model has
no native vision, so zai-vision is its eyes. The auditor prompted for concrete UX issues (copy,
hierarchy, touch targets, contrast, friction for a first-time non-technical user) and triaged the
results against the actual app code (file:line cited below).

## Findings by priority

> Each finding cites every screen it touches (de-duplicated) and a concrete recommendation. The
> screenshot filenames reference the evidence. File:line references are the **current** location of
> the offending copy/logic (verified against the code at audit time).

### P0 — blocks or confuses a first-time user

#### [P0] Pay tab (camera gate) — system-jargon permission copy stops users cold
**Screens:** `ux-pay-empty.png`, `ux-wallet-funded.png` (the default landing tab is Pay).

The Pay tab — the app's primary surface — opens to a near-empty scan area reading
**"camera permission needed"** with a button **"Grant camera"** (`app/components/QrScanner.tsx:21-22`).
For a first-time non-technical user this phrasing is the WORST-CASE intro to the app: it sounds like
a security prompt, gives no reason for the request, and uses the formal system verb "Grant" that no
consumer app uses. A meaningful subset of users will hesitate or refuse, and refusing locks them out
of the primary flow with no obvious recovery (the empty scan area just sits there).

The wallet-funded screenshot is materially worse for trust than it should be: a user who just created
a wallet sees a black box that says "camera permission needed" — the ∂100 balance is in the header,
but the center of the screen reads like an error.

**Recommendation:**
- Lead with the goal, then explain the ask: **"Point your camera at a payment code to pay"** with a
  secondary line **"dpay uses your camera only to scan codes — never records or uploads."**
- Button label → **"Allow camera scan"** or just **"Start scanning"** (drop "Grant").
- Consider an illustrative placeholder (a faint QR outline inside the scan area) so the empty state
  tells the user what to aim at.

This is the single highest-impact change in the audit — it re-frames the user's first impression of
the whole product.

### P1 — friction (user can recover, but it costs trust/taps)

#### [P1] Settings — raw "Relay URL" input is a footgun a curious user will trip
**Screens:** `ux-settings.png`.

The Settings sheet exposes a raw URL field labeled **"Relay URL"** prefilled with
`http://127.0.0.1:<port>` (in production it will be the real https relay URL) and an **Apply** button
(`app/components/SettingsSheet.tsx:75-90`). The label is jargon — a non-technical user has no mental
model for "relay" — and the field is one fat-fingered paste away from bricking the wallet against a
dead URL (which the audit's own `ux-offline-state.png` proves is the failure mode; the wallet then
shows `~ approx.` and no settled payments until the user reverses the change manually). The
description text ("The server your wallet talks to") helps but is below the input, not before.

**Recommendation:**
- Rename the field to **"Server"** (or hide it behind an "Advanced" disclosure that is **collapsed
  by default**).
- Move the helper text ABOVE the input so the user reads the consequence before they edit.
- Consider gating Apply behind a confirm dialog when the new URL differs from the last-known-good one
  ("This will switch your wallet to a different server. Continue?").

#### [P1] Deposit sheet — "—" placeholders for fee/min read as "broken/loading", not "zero/unknown"
**Screens:** `ux-deposit-sheet.png`.

The deposit instructions render **`Network fee — · Min deposit —`** when the fee/min are zero or
unavailable (`app/components/DepositSheet.tsx:144-145,189`). The em-dash is intentional (the code
comment says "render '—' for fee/min" rather than a misleading "0.00000000 BTC"), but to a user
it looks identical to a fetch-in-progress or a broken field. On a money screen, that ambiguity
directly costs trust at the moment we're asking the user to send real BTC.

**Recommendation:** replace the bare `—` with explicit language:
- fee unknown → `Network fee: not yet known`
- fee genuinely zero → `Network fee: none`
- min none → `No minimum`
The current "—" is correct in spirit (don't lie) but loses the user's confidence by being maximally
under-specified.

#### [P1] Receive QR — "Payer paid offline? Scan to settle." is unexplained, twice
**Screens:** `ux-receive.png`, `ux-offline-state.png`.

The link **"Payer paid offline? Scan to settle."** appears on the request-QR screen
(`app/components/ReceiveMode.tsx:167`) and stays visible while waiting. A first-time user has no
idea what "settle" means, what to scan (a receipt? a payer's phone? an NFC tap?), or why the option
exists. The wording is correct for the offline-NFC handoff (flow 20 covers it) but reads as
insider-jargon to anyone outside that flow.

**Recommendation:** either (a) hide the link until an NFC tap is detected (so it appears in context,
not as a permanent mysterious option), or (b) rephrase to a one-line concrete action: **"If the
payer paid without scanning your code, tap here to confirm with their phone."** A short subtext line
("for NFC or offline handoffs") would resolve the jargon.

#### [P1] Transactions empty state — "No transactions yet" is a dead end
**Screens:** `ux-transactions-empty.png`.

A freshly-onboarded user who taps the Transactions tab sees a single gray line: **"No transactions
yet"** (`app/components/Ledger.tsx:23`). The tabs (Pay/Receive/Transactions) are visible so the user
*can* recover, but the empty state teaches them nothing and feels like a blank wall — the worst
moment to lose a user is right after they install.

**Recommendation:** make the empty state a guidepost:
> "No payments yet.
> Tap **Receive** to create a payment request, or **Pay** to scan one."

One line of copy, no new components, converts a dead end into a next step.

#### [P1] Currency glyph ∂ is confusable, and the wallet layout reinforces the confusion
**Screens:** `ux-wallet-funded.png`, `ux-pay-amount.png`, `ux-transactions-empty.png`,
`ux-transactions-populated.png`, `ux-receive-amount.png`, `ux-balances-sheet.png`,
`ux-offline-state.png`.

The DEMO currency uses the partial-derivative glyph **∂** (`app/lib/format.ts:14`,
`app/config/catalog.ts:269`). The choice is intentional ("a D-like glyph distinct from BTC's ₿") and
well-documented in code. The vision MCP, however, misread it as **δ / ð / ʘ / ₹ / d** in different
screenshots — i.e. even a capable OCR reliably misclassifies it. On `ux-wallet-funded.png` the
glyph + amount + adjacent username ("Sato") rendered to vision as **"balance of 0100.00 in a
currency called Sato"**. Real users won't OCR the screen, but they will glance, and an unfamiliar
glyph slows recognition of the single most-important number on the screen.

**Recommendation:** keep ∂ for now (changing it ripples through golden wire tests) but mitigate:
- Put a one-time, in-onboarding explanation: "∂ is the demo currency — play money, $1 = ∂1" near
  the funded amount.
- Increase the visual separation between the wordmark "dpay" and the username "Sato" in the header
  (currently the username sits so close that vision read the pair as `dpay / Sato = currency name`).
  A small "·" separator or moving the username to its own labeled row ("Account: Sato") would fix
  the misread.

### P2 — polish (would improve, not block)

#### [P2] Balances hub — "Send BTC on Bitcoin" / "Send USDC on Ethereum" subtitle is redundant + jargony
**Screens:** `ux-balances-sheet.png`.

The per-asset subtitle reads **"Send BTC on Bitcoin"** / **"Send USDC on Ethereum"**
(`app/components/BalancesSheet.tsx:73`) — a tautology in the BTC case ("BTC on Bitcoin") and a
network-name that means nothing to a non-technical user in both cases. The DEMO row's
"play money for testing" copy, by contrast, is excellent.

**Recommendation:** rewrite as user-benefit, not network-topology:
- BTC → **"Bitcoin, in your wallet"** (or just **"Wrapped Bitcoin"**)
- USDC → **"US dollar stablecoin"**
- USDT → same pattern.

#### [P2] Balances hub — two-instruction subtitle crammed into one line
**Screens:** `ux-balances-sheet.png`.

The header subtitle reads **"Tap a currency to show it on your home screen. Top up any of them
below."** (`app/components/BalancesSheet.tsx:47`). Two instructions in one sentence; the first
(tap-to-set-home-currency) is a discoverability hint for a non-obvious feature and gets buried by
the second (top-up). Most users will only read the second.

**Recommendation:** split, or surface the tap-to-set-home behavior as an explicit per-row affordance
(a "Show on home" toggle / star icon next to each row).

#### [P2] Receive QR — "Show this to the payer" + "Waiting for payment…" lack visual feedback
**Screens:** `ux-receive.png`, `ux-offline-state.png`.

The request-QR screen shows static text **"Show this to the payer"** + **"Waiting for payment…"**
(`app/components/ReceiveMode.tsx:149,163`) with no spinner, no "reconnecting" indicator, and no
explanation of what happens at timeout. In the offline-state capture this is materially worse: the
relay is unreachable, but the screen looks identical to the online waiting state. The only
distinguishable offline cue is the header `~` — easy to miss.

**Recommendation:** add a small connection-status pill on this screen (mirrors the header's
`~ approx.` but contextual: "Offline — reconnecting…"). When the QR expires, swap the body to
"Code expired — tap New request" rather than leaving the user to discover the timer's meaning.

#### [P2] Transactions row — 24-hour GMT+offset timestamp is unfriendly
**Screens:** `ux-transactions-populated.png`.

The history row renders the time as **"13:19 GMT+2"**. Most consumer wallets render either relative
("Today, 1:19 PM") or locale-formatted; raw GMT offsets are a developer affordance. The flow-28 fix
already standardized GMT formatting for `fmtTime`, but the user-facing label could be friendlier.

**Recommendation:** render "Today, 1:19 PM" / "Yesterday" / "Mon D" — the locale defaults do this
for free.

#### [P2] Onboarding — "Create & fund wallet" button can read as "you must add funds"
**Screens:** `ux-onboarding-empty.png`, `ux-onboarding-filled.png`.

The primary CTA reads **"Create & fund wallet"** (`app/components/Onboarding.tsx:46`). The subtext
("Creates your wallet and adds $100 in demo funds to get started") clarifies, but the button label
alone can read as "you'll need to fund this with your own money" — a friction point for a user
deciding whether to commit. The accessibilityLabel ("Create and fund wallet") shares the issue.

**Recommendation:** shorten to **"Create wallet"** — the subtext carries the demo-funds news. Or
lead with benefit: **"Get my free wallet"** (the founder's positioning is "non-custodial + free to
try"; the button should reflect that).

#### [P2] Paid ✓ screen — Cancel/dismiss path is visually weaker than Approve
**Screens:** `ux-pay-amount.png` (review, pre-Paid).

On the review screen, **Approve** is a large brand-green button; **Cancel** is small gray text
underneath. Approve being primary is correct, but the asymmetry is steep enough that a user
surprised by the amount may tap Approve by reflex before finding Cancel. (This is the standard
consumer-wallet pattern, so the issue is minor — listed for completeness.)

**Recommendation:** make Cancel a bordered secondary button of the same width as Approve, just
below it, so the tap targets are equivalent and the user makes a deliberate choice.

#### [P2] Reset wallet — the visual cue understates the consequence
**Screens:** `ux-settings.png`.

The Settings sheet shows **"Reset wallet"** in red link text (`app/components/SettingsSheet.tsx:54`).
Clicking it does open a confirmation dialog (`btn-reset-confirm`, with the excellent
`accessibilityHint` "Permanently erase your wallet from this device — funds become irrecoverable"
at line 46) — so this is NOT the P0 the vision MCP flagged (it could not see the dialog from the
closed-state screenshot). The remaining issue is that the entry-point is a quiet red text link,
visually equivalent to "Privacy policy" above it. A user exploring Settings could tap it lightly.

**Recommendation:** keep the confirmation (it's the right gate) but make the entry-point visually
distinct from "Privacy policy" — e.g. a bordered red button "Reset wallet…" with the ellipsis
signaling "this opens a dialog".

## What's working well (preserve these)

- **Paid ✓ confirmation** (`ux-pay-paid.png`): full-screen green check + "Paid ✓ ∂25.00" +
  recipient name + "New payment" CTA. Textbook clear success state — the visual hierarchy leaves
  zero ambiguity about the outcome. The recipient name (not "merchant") is the L6 fix and it shows.
- **"dpay never holds your keys — funds mint 1:1 to your wallet on confirmation"** copy on the
  deposit sheet. This is the trust message a non-custodial wallet MUST lead with, and it's placed
  exactly where the user is about to send real BTC.
- **Copy address button** on the deposit sheet — long BTC addresses are intimidating; the
  prominent green **"Copy address"** button means a user never has to manually select/transcribe
  the string. Paired with the QR, both copy-paste and scan paths are first-class.
- **Reset confirmation copy** — "Permanently erase your wallet from this device — funds become
  irrecoverable" is exactly the right severity. (Vision missed it because the dialog isn't open in
  the screenshot; flow `12-settings` proves it fires.)
- **Active-tab visual treatment** — the brand-green highlight on the active tab is unambiguous
  across all 14 screenshots.
- **"Valid for ~5 min" timer** on the request QR — gives the user a clear expectation without
  exposing the underlying expiry mechanics.

## Out-of-scope notes (so the founder doesn't chase these)

- **"Press Esc to close"** appears at the bottom of every sheet in the web build. It is gated by
  `Platform.OS === 'web'` (`BalancesSheet.tsx:139`, `SettingsSheet.tsx:102`, `DepositSheet.tsx:237`,
  `WithdrawSheet.tsx:175`, `CkErc20DepositSheet.tsx:420`) — i.e. it is web-only and **does NOT
  render on the Android production target**. The vision MCP flagged it as mobile-inappropriate;
  that's correct for the screenshot but the prod APK doesn't ship it. No action needed.
- **`http://127.0.0.1:<port>` as the relay URL** is a test-harness artifact (the real relay URL is
  `https://...` in production). The Relay-URL-is-a-footgun finding (P1 above) stands, but the
  literal `127.0.0.1` value is not what end users see.
- **Reset wallet "no confirmation" false positive** — the vision MCP claimed Reset has no
  confirmation. Flow `12-settings` and `SettingsSheet.tsx:46` prove it DOES (with strong warning
  copy). The P2 finding above is about the visual weight of the entry-point, not a missing gate.
- **"Approve is too easy to tap by accident" (P2)** is a standard consumer-wallet pattern; flagged
  for completeness, not a regression.
